# [FORMAT] - The Lesson Page structure & formatting contract -
	- Changes to this file must follow [explicit user instructions] OR [explicit user sign-off] 
    - This file's guidelines are [Maximally generalised] to [apply to] but not [overly restrict the possibilities] of content generation. 
    - This file drives content-aware formatting/organization/separation lesson pages.
    - Elements which exist because a FUNCTION creates them are styled by style.css and driven by FUNCTION.md guidelines.
	- PAGE SHELL:`_shell.html` (repo root) is copied and its five placeholders filled: {% raw %}`{{TRACK_TITLE}}` (document title, e.g. `Adult`), `{{TRACK_UPPER}}` (h1 top line), `{{TRACK}}` (the `TRACK` constant), `{{L}}` (the lesson number), `{{LESSON_TITLE}}` (the content `<h1>`){% endraw %}. A finished page's shell is NOT a template.

## Standard [ELEMENT] formatting guidance
- The lesson title (h1) must be written short enough to sit on ONE line -(fixed 38px size inside the 1200px content area).
- When used, mark Portuguese text and make it italic with `lang="pt"` (CSS `:lang(pt){font-style:italic}`), `.pt`(explanations),`.ptw`(in exercises) or `<i>` as a fallback. 
- Items within a block must not overflow the block or overlap/touch each other.
- Lesson sections are numbered `1.`… (h2). 
- Blocks are lettered inside-top with [`A. `(h3)] , restarting at A in every section. **The header is the block's first line and sits above the block's content in every block of every lesson** — nothing a vehicle, script or stylesheet draws into the block may take that place, so a game that inserts its own stage inserts it BELOW the header and never above it.
- Exercise/activity/quiz items are numbered `1..n`, top to bottom then left to right, restarting in every block.
- **An item's option count is set by what it has to discriminate, never by habit.** Two or more options, always: 3–4 is the baseline, 2 is right when the pair is genuinely binary, and 5–6 belong to an item whose content supplies that many plausible candidates (a family of ten look-phrases, six tense forms). The vehicle's own maximum binds and is stated in its CONTENT_EXAMPLES entry (`whackMole` draws one mole per option: 2–6). Difficulty is the other limit — the count rises with the discrimination the lesson intends, not with the wish to fill a grid. **That entry also carries the activity's `load` multiplier** — what the count, the clock and the one-chance rule each add — which a build multiplies by the block's content level to read the block's total load (`PEDAGOGY-MAP.md [LEVEL] x`). The activity states the number; a build never estimates one.
- **Every training block declares its move**, `data-move` on the block element, one value: `spot` (find the right one among decoys), `choose` (pick the form that fits a stated situation), `produce` (write the language yourself), `correct` (find and fix what is wrong), `contrast` (decide between two forms that are confused), `recall` (retrieve something taught in an earlier lesson, marked `data-recalls="<pid>"`). A `produce` block carries an `input.gap` inside a sentence or a `textarea` other than `#feed` — a radio-only block cannot be `produce`. A block that trains nothing (a chart of reference, a dialogue, a scenario) declares no move.
- For any section and/or block, a concise text below the header [[explains its contents] or [instructs the student what to do]] ONLY IF [[defensibly helpful to the student] AND [doesnt re-state anything else in the lesson]]. 
- An item may never ask for a judgement on an axis the page never defined before the item asks for it. the item and its column headers may not be labelled with a word invented for the table.
- Any fill-in hint/gloss sits below and center-aligned with the center of its respective input field.
- Font sizes are fixed constants (no viewport-relative sizing).
- **The type default is SERIF, site-wide.** An exception is `--ui-tight`, used only by the game chrome (`.g4-*`) at 9–13px in fixed-size tiles, where the text is an instrument panel rather than prose and a face swap would move metrics inside boxes that cannot grow. A lesson author never reaches for a font: the face is the stylesheet's, alone.
- **A track folder's NAME is URL-, selector- and CLI-safe; its DISPLAY name is data.** The folder name is lowercase with hyphens or underscores (`advanced-stem`), never a space, because it travels as a URL path, a `--track=` argument, an `id` suffix and a `data-*` value. The name a person reads lives in that folder's `track.json` `label`, which is free to carry spaces, accents and an arrow (`English → Basic Portuguese`), so nothing about the display ever forces a rename. **A folder name is chosen once**: the teacher's access sheet stores the track name itself, so renaming a folder orphans every grant that mentions it (a hyphen is safe everywhere; a space is not).
- Sizing philosophy: Minimum size an average person comfortably sees, clicks, reads.
- **A focus ring is opt-in, never a consequence of holding a key.** No element may draw a focus outline unless `<html>` carries `.kbd`, which only a real NAVIGATION key sets (Tab, arrows, Home/End, PgUp/PgDn, Enter, Space, Escape) — the gate is duplicated at the top of `engine1.js` and in `index.html`, and a pointer press clears it. A bare modifier (Shift/Ctrl/Alt/Meta) is not navigation and must never draw a ring, which is why `style.css` also suppresses the browser's own UA ring while `.kbd` is absent. A new rule therefore never writes a bare `:focus` or `:focus-visible` selector: it is `html.kbd …` or nothing, and `qa/landing.mjs` fails if an ungated ring rule appears anywhere in the stylesheet.


### Mechanical [LIMITS]— each prevents an answer or a line from being lost
- Every control that carries an answer (`input.gap`, radio, authored `textarea`) resolves exactly ONE anchor: an unanchored control is never saved, and two controls on the same anchor+place overwrite each other.
- Question stems are unique within a block — a repeated stem gives two controls one saved answer.
- A `textarea` inside `.content-area` is (`resize:none`). the page never reflows, no items are resizeable. 
- If unbuilt work occurs, it is marked, never faked.

### Following are guidance **IF** relevant content used
- .thsub = a chart-column-header subtitle (the second line under the main label): block, weight 400, smaller, reduced opacity.
- input.gap = fill-in blank: transparent, 2px tan bottom border, #fff8ea bg — a CONTIGUOUS line, never literal "___" underscores in the prompt
- `data-answer="make me|and?|so?"` = the key for a typed control, pipes separating the accepted forms; `name="a1c1"` is the item's number (section 1, block C, item 1), so an item and its key are one id. **Complete** reveals each key on its own line under its field and locks the page; **Clear page** empties the answers, the keys and the lock. A key is never a hidden input — the answer layer would save it as the student's answer.
- `lang="pt" data-why="necessary|optimal"` = a Portuguese gloss that passes e)'s test; `qa/lang.mjs` exempts it from the PT share, so an unjustified gloss still has to be defended.
- .chart = structured data table (cognate rules, phrase translations, to-be chunks, false friends): paper, ink header row, tan grid. **A chart is an IN-BLOCK class, never a block**: it is a `<table class="chart">` inside a `.panel` / `.card` / `.game` / `.dialog`, and the block around it carries the width, the outline and the shadow — so inside a block the chart draws no frame and no shadow of its own.
- .chips = wrapping keyword pills ("quase iguais" list)
- .itemsize-half (593px) / .itemsize-third (391px) / .itemsize-twothird (791px) = the half-, third- and two-thirds-width slots, set on each block inside a `.itemrow` — PREFERRED when the content is a comparison or a contrast, or a set of ideas / vocabulary classes that exist in two or three distinct forms, one form or class per column so the parallel is visible. **The three-way pairing is `.itemsize-third` + `.itemsize-twothird` in one `.itemrow[data-cols="2"]`** — a vertical vocabulary list in the third, the exercise that uses it in the two-thirds. No `.grid3` exists: no rule implements it.
- .blanks = wrapping row of fill-in pairs (word + input.gap)
- .dialog = dialogue block: #fff8ea fill, rose frame, bold speaker labels. **Speaker names are English given names** (Josh, Maya, Leo, Sam, Ash, Dee) — never Portuguese or Brazilian ones (Téo, Guh, Thiago, Luiz, Bia), whatever the scene is about: the student is learning English in an English world, so a name that only exists in Portuguese makes the scene Portuguese again.
- .listen = compact ▶ audio chip placed inline beside what it speaks
- A fill-in hint/gloss (Portuguese, italic) sits on its own line BELOW the input. Author it with the block fill-in layout (`.blanks.sent` / `.blanks.sent.cols`) so the line break actually renders — a `<br>` inside the default flex `.blanks` row is ignored.
- @media print: hides header/#controlbar/#feed/footer, strips container border/shadow
- .card: paper bg, 2px ink border, 16px radius, 5px 5px 0 tan hard shadow

## [GENERATION] (width & fill techniques; CSS stays fixed)
a) Width: a block takes ONE of FOUR slot widths inside the fixed 1200px content area, with a 14px row gap — full 1200 · half (1200 − 14)/2 = 593 · third (1200 − 2×14)/3 = 391 · two-thirds (1200 − 14)×2/3 = 791, and a third that shares its row with a two-thirds is (1200 − 14)/3 = 395 (CSS implements exactly that: `.itemsize` 100%, `.itemsize-half` `calc(50% - 7px)`, `.itemsize-third` `calc(33.3333% - 9.3333px)`, `.itemsize-twothird` `calc(66.6667% - 9.3333px)`, and inside `.itemrow[data-cols="2"]` a third tightens to `calc(33.3333% - 4.6667px)` so the pair sums to 1200). Siblings in one `.itemrow` are equal unless they are a third beside a two-thirds. A block MAY sit beside another block that shares its row. A lone half-, third- or two-thirds block is CENTERED in the content area — it never sits against the left edge with the dead space all on one side.
b) Priority is minimizing dead space.
c) Block width decisions are content-aware of what they contain AND context aware of adjacent blocks - If any block must be made half-width and an adjacent block COULD be made half width, do so and pair the two blocks horizontally per (a).
d) Adjacent blocks of different heights should be analysed to determine the quantity (and type) of (real, relevant) content that could be added to extend the shorter of the two and trigger a 'cleanup' generation step to do so.
e) Fill is a decision, made before the block is written. Read the block's CONTENT only — its chart, table, item list, options. Explanatory or flavour text (an intro line, a note, a gloss, a `.thsub`) does NOT count: it wraps to whatever width it is given, so it can never be the reason a block stays full width.
   1. PAIR FIRST. Before asking how wide one block should be, ask what could stand beside it: a vocabulary list beside the exercise that drills it (`.itemsize-third` + `.itemsize-twothird`), two contrastive rules, two classes of one form, a chart beside its questions. Two blocks sharing a row is one row of content with no dead space, and it is preferred to either block alone at full width.
   2. THEN MEASURE. A full-width block whose content, set at its natural line length, occupies under 50% of 1200px is wrong: give it a half, a third or a two-thirds, and centre it if it is alone on its row (a). Between 50% and 70% is acceptable; reflow/tiling to a better fill is preferred. If a list is reflowed into columns (j), numbers run down each column and continue at the top of the next — never across.
   3. NEVER PAD TO FILL. Short content in a wide block is a width decision, not a writing problem: no added sentence, no stretched option, no invented row to reach the edge.
   A row's slots must sum to its width — two halves, a third beside a two-thirds, or three thirds. Never a half beside a third.
f) Consecutive questions are separated by a small, consistent vertical gap.
g) A note that applies to one chart row CAN be a merged row directly under it: `<tr class="note"><td colspan="N">…</td></tr>` — a bare row spliced into `<tbody>` will not span.
h) Contrasting [linguistic, phonetic, or grammatical] [classes, categories, or concepts] are made visually distinct (using columns, spacing, block separation, or colors as appropriate) so the contrast reads - **This does not supersede 'professional-looking results' goal of 'layout STANDARDS' or other formatting rules**. 
i) **A chart is never a block.** It is a child inside one (`.panel .chart` = the block’s width minus its 20px side margin) and the block around it takes one of the four widths in (a) — a generated lesson never writes a `.chart` straight into a section. Column count and row shapes are content-aware, never fixed by CSS.
j) Reflow: a reflowed block states `--rows` (items per column, e.g. `--rows:2`) in its own style attribute — never on a section or wrapper, so a section can never be split into columns; the column count follows from the item count.
k) A lettered block is a VISIBLE block: its content sits inside a framed container — `.panel` (or `.card`) when the inside is `.qgrid` / `.blanks` / `.chips`, or the block IS `.game` / `.dialog` / `.card`. `.qgrid` and `.blanks` carry no frame in CSS, so unwrapped they read as loose page text instead of a block.
l) **Every block declares its KIND, on the block element: `data-kind="teaching"` / `"mixed"` / `"training"` / `"games"`**, copied from the `## [...]` category the vehicle sits in on CONTENT_EXAMPLES.md — the tag is the category, never a second opinion about the page. The kind decides the outline only: **teaching keeps the ink outline, mixed and training take the orange one, games take the purple one** (`--orange`, `--purple`). An untagged block keeps the edge its container always had (a panel's tan, a card's or a game's ink, a dialog's rose), so nothing generated before this rule changes shape. It sits on the block, beside `class` and `style`, exactly like `itemsize` and `data-move`.
m) **A block's width is authored on the vehicle's entry, in a `**width**` field, as the vehicle's block ladder — and the row breaks fall out of the arithmetic.** The value lists the vehicle's blocks in page order joined by `+`; a row closes by itself the moment its slots sum to 100% (e), so there is no per-row token and no separator. Each block states one slot, or `<slot>->` when that slot is the default and the block may grow **in steps, as far as full**. Real values: `half+half` (twoWordVerb, one row) · `full+full` (registerContrast, two rows) · `half+half+full` (pronLab = `[half half]` then `[full]`) · `third+twothird` (infoGap, one row) · `third+third+third+full` (songStructure) · `half->` (formFill, one block that may grow). Three consequences bind a build: **the ladder is the vehicle's, so it is authored per vehicle and never derived from its block count** (two vehicles with two blocks each may differ entirely); **the pairing is binding, so a lesson never breaks a single block out of a pair** — a lone block uses a single-block vehicle or a primitive; and **the entry's prose states the shape, not the widths** (`a chart block beside the matching exercise`), because the field is the only place a width is written. The measuring step that would choose widths by itself is not part of this rule — see the open question in `PENDING.md [17]`.
n2) **A row's children ARE the blocks.** Never a wrapper `div` carrying the width class with the block inside it: `.itemrow` stretches its children, so the wrapper grows and the block inside it stays short, and a pair that should match ends 50px apart (that was `infoGap`, measured). Put `itemsize-*` and `data-kind` on the block itself.
n) **Activity blocks are outlined, not dashed.** `.panel`/`.card`/`.game`/`.dialog` carry a 2px solid edge (`--edge`, set by the block's kind) and a 4px offset hard shadow. Nothing that reads as a block may use a dashed border; the only dashed line left in the sheet is `.game-stage`, a field of play *inside* a game.
