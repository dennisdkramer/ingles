## CLOSED
- [CLOSED 2026-10-12] "Edited-note Save does nothing" (owner retest: first save works, Add/Edit Note opens, Save on the edited note is a no-op). ROOT CAUSE — `nbSaveNote` sent `action:"add"` with NO id, so every Save APPENDED a second `note` row with a fresh id while the ORIGINAL row stayed; the popup's note lookup (`nbNoteText` → `nbEntries(...).find(...)`) returns the FIRST matching row, i.e. the original note, so the refresh redrew the OLD text — and rows piled up. FIX: ONE shared core save `nbUpsert(t,type,fields)` (engine1.js): 💾 Save and `rec()` both use it; it re-uses the id of the row already stored for that anchor+type (server add/set deletes the row with that id first → replace, never duplicate), updates the local `layer` immediately so the popup shows the new text at once, then `send()` (network last). Code.gs add/set now also `purgeDrive_`s the Drive file of the row it replaces, so a re-record does not leak the previous clip. QA (qa/smoke.mjs) now saves an edited note and asserts ONE note row with the new text + Save greying out again, and that re-recording reuses the stored `rec` row id. See HARNESS RULE 11.

- [CLOSED 2026-10-12] Recordings STILL not in Drive after the earlier fix (owner retest: clip playable right after recording, then "no saved audio" after a refresh). TWO causes. (a) The `backend/Code.gs` fix only runs from the Apps Script DEPLOYMENT: it must be redeployed (Deploy → Manage deployments → new version) — pushing the repo does not update it. (b) A REAL read-side gap that also broke reachable rows: GET `?action=layer` returned only `fileId` and DROPPED the inline `b64` fallback, so any row without a `drive:<fileId>` pointer came back with no audio at all (`fileId:""`, `b64` undefined) while the phrase still looked saved — `nbPlayRecording` then dead-ended with "⚠ não consegui carregar o áudio". FIX: layer now returns each recording as `fileId` (Drive) or `b64` (inline fallback); a re-record reuses the row id via `nbUpsert` so the first-match lookup can no longer play a stale earlier clip. MANDATORY: redeploy the Apps Script version for the backend half to take effect.

- [CLOSED 2026-10-12] Recordings "working and replayable locally but not being saved to the drive". NOTE: the backend ships from `backend/Code.gs` but runs from the Apps Script deployment — it must be redeployed (Deploy → Manage deployments → new version) for the fix to go live; the client (engine/style) redeploys with the GitHub Pages push. - [CLOSED 2026-10-12] Colour-select palette (`.pop.hlpalpop`) stopped appearing on Ctrl+drag highlights after rework #2, while the highlight itself still worked (the exact owner report: text gets highlighted, no colour swatches). ROOT CAUSE — reproduced in a real browser (headless Chrome driven over CDP with `Input.dispatchMouseEvent`/`Input.dispatchKeyEvent`, since jsdom stays green on this: it has no keyboard timing) — the reworked gesture builds the palette synchronously at mouseup, i.e. with Ctrl STILL HELD, and the global `keydown` handler closed the palette on ANY keydown: the auto-repeat keydown the keyboard keeps sending while Ctrl stays down lands milliseconds after the palette is born and killed it. The pre-rework code only dodged this by timing (it built the palette ~350ms after the selection settled, by which time Ctrl had usually been released). FIX: Ctrl/Meta keydowns no longer close the palette (they are the gesture's own key, held and repeating exactly when the palette appears); any other key press and any click elsewhere still close it, and a swatch still recolours + closes. FUNCTION.md palette rule updated with the exception; qa/smoke.mjs now asserts that a Control/Meta keydown (`repeat:true`) leaves the palette open and that any other key still closes it. CDP evidence: palette present and on screen right after the gesture (box 245,370 88x36, 3 swatches) and STILL present after the Ctrl repeat + keyup.
