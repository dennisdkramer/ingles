Pass 2 — Style, Mechanics, Structure

Sections divide concepts, blocks divide for organization

Let a cell hold several items when they belong together: the point of the cell is that something can be dragged beside it, not that it holds one thing.

Use positional contrast— opposites or two tenses side by side,  an element set apart so it is seen as distinct.

The text on this page is illustrative and pertains to mechanics and structure. Nothing here is an example or reference for prose. 

.row is only the utility for a line of chips or buttons — .rows and their cells are reserved as page layout elements

Every element in this section is drawn with the markup that builds it. Its item count is the example's own, never a count to copy.

Pass 2 may: fix errors, split a massive text block, group or rearrange items to improve flow, add training items. Add instances, never a proposition — another useful example of a rule the page already states, the exception that rule carries, a contrast— written in the drafted level, register and voice. 

Build what the notes name, and then delete them. A note says what its element carries — a chart's rows, who speaks each line, the words a key sits above, the sentence to mark, the song's line — and the element is built from that, never re-decided.

Author no flex and no width on a cell: the page sizes the line when it loads, and an authored width is stale on the next screen. Give the width to whatever needs it — a cell holding a chart, a table or long answer lines takes its share first.

Block styling, sizing and layout choice

Everything on the page is organized by 3 layers of flexbox rows. The first layer wraps everything in a horizontal row inside the .content-area. The cells within it - like this block - are wrapped as in a layer 2 row.  The rows and cells allow content - images, activities, tables, and paragraphs - to be placed adjascent and fit and flow naturally. This is the default block look with no data-look defined.

How the blocks sit on the page

Text that applies to the whole section may live outside of a block, or it may be data-look="float".

Declare data-look on the block, never infer it from what it holds: it changes the paint only.
Default text behaviour is full justify, but short strings and text in thin containers often looks better centered.

Dark

'Night mode' block, used optionally for content that relates to the night or night life. data-look="dark"

Tint

data-look="tint"
For content that is specific to the track - Technical terms that only the business track will use, youth slang that only the kids track will use, etc..

Outline

For highly important or interesting content that should stand out data-look="outline".

Activity

For an activity — the block the student works in: typing, ticking, clicking a card. Not for text: stripes behind three paragraphs make them harder to read. data-look="stripes".

Tape

For a note pinned onto the page — a tip, an aside, a reminder read on the way past. Not for the lesson's own teaching, and never two in one row. data-look="tape".

The Games

Don’t add a game just to have one. A game is a skin over an activity the lesson already wanted: the activity is chosen first, and a reskinned game is that activity in another skin, never an element of its own. Use one only where it is materially better than the plain activity.

A .game draws its own edge, so it stands at page level and is never put inside a .block. Every game reads the same content — .game-list > .qitem, each with a .qstem and radio options, data-a marking the right one — so that list is what prints and what the student answers if the script never runs; data-game chooses only the presentation, never the content. A game in a quiz section carries data-retry="0"; a training game carries nothing. A .listen in the item's stem makes the round SPOKEN: the runner says its data-say on the frame the round opens and keeps a 🔊 replay on the HUD, so a game can ask "which word did you hear?" — data-sound="0" mutes both, and bingoCard is the one presentation that times its own clip and is left alone.

Verify

  • No option set leaves one option wrapped alone under the rest: four options read 4×1, 2×2 or 1×4.
  • Check every block, class and attribute against this page: an element this page does not draw is not used, and a class remembered from another page is not used.
  • For a music section: its recording has a provenance row in assets/README.md, and the section teaches something the sound carries.
  • Every translation reads as a Brazilian colleague would write it — a calque, a wrong tense or a missing subjunctive is a defect.
  • Read the source for a directive comment left in the page — TRAIN_HERE, QUIZ_HERE, MUSIC_HERE, MAP_HERE, DIALOG_HERE: it was never built, or it was built and the comment never deleted.

The batch's mechanical checks follow — npm run page, npm run build:lessons — and a failure is repaired in its own lesson. The lesson is finished when this is clean, and it is not opened again in the task; alignment is the batch's, at the end.

Align

Once every lesson in the batch is finished and its checks are green, npm run align -- --track=<track> --lessons=<range> measures the pages on the rendered page, and the batch is aligned before it is committed and pushed. It reads the working tree through a local static server — what is about to be published, never a deployed copy.

Heights come from the authored page and widths from the solved one. equalize.js makes a lopsided row look level, so a height read from the finished page measures the solver: the pass calls EqualizeRows.clean() for the authored heights and reads the solved widths, where a cell is actually squeezed. A row is uneven when its two cells differ by more than 30px of content — the tolerance a reader does not notice — and a row of one cell is not measured. A cell short of width is repaired structurally: the row is broken, or the wide cell is given the line. A cell short of content takes content.

The repair goes in the shorter cell, and it is content — but only after the pairing is checked. First read the row against the rule that made it: if the two cells were paired for size, balance or a filled line, the pairing was never a claim about content and the row is broken. Where the pairing is real, an activity takes another item of the kind it runs — the case it has not asked for, the exception the section named — and a teaching cell takes the example, the contrast or the note the section stopped short of; it may also take an open-licence picture, cropped to what the cell asks for, kept in assets/ with its credit line. Rewrapping comes last: a line is not cut to reach a height, and a headline that comes out cut short is reworded shorter and never left cut.

Inside an activity is read as well: a question standing far taller than its neighbours in a .qgrid is the same imbalance, and the repair is a question moved out of the grid onto its own line, never a question shortened to fit a share of the page. The pass repeats until it prints no row above 30px; then npm run page and build:lessons run again, and the batch is committed and pushed with the alignment stated in the commit message. build:lessons writes lessons.json and tracks.json from the page filenames — a page pushed without that run is live but unlisted — and stamps every page that links style.css or equalize.js with the file's own hash, so a changed sheet is fetched on the next load.
