## CONTENT MAP
- Lesson pages are content-only: config consts (TRACK, LESSON, SECRET, BACKPACK…) + the engine includes; every lesson's prose, sections, exercises and widgets live in the page file itself.
- **Fixed page skeleton vs. derived content.** The only mandatory page parts are the mechanical skeleton: doctype/head/title/stylesheet, #toast, header.brand, #controlbar, main#page → .page-container → .content-area, the centered h1, the footer, the closing script block (BACKPACK/SECRET/TRACK/L/COUNT + engine1.js/engine2.js + the engine-load guard), and the #feed (shared notebook) and #trw (translation textarea) boxes, which the harness requires. Everything else — every section (including any opening "abertura"), block and exercise group — is derived content, generated from the pedagogical principle and included only if it earns its place. The quiz is the standard ~20-min end-cap; its contents are whatever tests the lesson. Site-usage instructions (highlight/note/record gestures) are not lesson content — they live in the control bar (ISSUES B-I9).
- Tracks: kids/ · business/ · nsfw/ — each lesson is a standalone page; business/lesson1.html–lesson34.html are the current build (a single 34-lesson progression), each with a `<lesson>.edit.html` sidecar.
- A translation textarea (the `#trw`-style box) is the student's own written work and is persisted like every other exercise input. It is a REUSABLE exercise shape, not a fixed one-per-page slot: a lesson includes as many as appropriate, in Treino and/or Quiz.
- Exercise layout (the reusable template — mechanism in style.css): every exercise group is a bordered panel inside a two-per-row flow, and a group that needs full width (long options / a textarea / many items) spans the whole row. Inside a panel there are two established shapes: (1) multiple-choice → an aligned grid of [number][stem][one column per option], so the options line up vertically; (2) fill-in → an auto-flowing grid where the prompt sits in a fixed-width column so every gap lines up, and the number of pairs per row is whatever fits the group's item width. These are NOT a closed set — a new exercise shape is allowed when it serves the pedagogy (record it here and in FORMAT.md when introduced). A page only declares a group's type and width — it never hand-tunes columns.
- Edit mode (teacher-only, in the "demo (you)" view): a ✏️ Edit toggle loads a separate unmarked, editable copy — the live page and its marks are never touched. Changes auto-save to the backend as a `type:"content"` row holding the FULL page HTML, keyed to the teacher's email (staging only; students never see it), and ↩️ Revert discards them. Every lesson file is created with a sibling `<lesson>.edit.html` sidecar that is a full copy of the lesson. "Baking in" is a pure rename: the editor fetches the saved HTML from the backend, writes it over the sidecar, deletes the original lesson file, and renames the sidecar to the lesson name — no copy/paste and no content editing.

## Pedagogical guidance — WHAT to teach and its order

### Lesson synthesis (before generating any block)
Each lesson is a deep, thorough pedagogical synthesis — never a template fill-in and never a copy of a neighboring lesson's structure. Start from the pedagogical principle, situate it against the content of the other lessons (what the student already knows and what comes next), and — whenever possible — research several outside sources on the lesson's topic to brainstorm ideas, not to copy. Before authoring a single block: (1) decide what the student must already understand (prerequisites) and teach it first; (2) choose the cleanest concept order (concrete/transparent → abstract/idiomatic); (3) decide the appropriate SET and QUANTITY of items — enough to build the system and fill ~60 min of pre-quiz content, never a fixed count; (4) plan how each item is presented (meaning/use, register, context, required prepositions attached and marked); (5) plan enough varied practice to build comfort and intuition, then the ~20-min quiz. Research and reason about the topic; owner-named items are pointers, not deliverables (HARNESS RULE 1). Make structural changes — add, remove or reorder columns, blocks and sections — whenever the pedagogy warrants it; the block template is a starting point, not a constraint.

## Generative guidance — HOW to generate, structure, format

### Content generation process (every block)
Content is produced by a loop; layout is never pre-assigned and never forced by CSS — a block BECOMES full-width, half-width, one column or several columns as a RESULT of this loop.

**Default:** a content-generation request implicitly includes the whole loop — steps 4 and 5 (alter/extend + structural re-check) are ALWAYS run afterward, unless the owner explicitly directs otherwise. Running only the generation pass (and skipping the 4–5 pass) is not "done".

**Intent notes.** "look at / take a look at" a block or page means READ and REASON about its HTML/content — never render or screenshot it (the agent has no vision). A short target label ("6A", "5.6A", "block A") that could point at more than one lesson/section/block must be clarified before acting, never guessed (see HARNESS.md RULE 1).

**Malleability.** There are no fixed shapes for activities or blocks, and no fixed exercise types per lesson. Every layout — a chart, a panel, a dialogue, a fill-in grid, the three-column fill-in (prompt right-justified | field | after left-justified), a multi-column item grid, a wide sentence-length field — is an OPTION, chosen during the step-3/4/5 pass to fit the content and the structural result. Flexibility and optionality apply to ALL page content; a block's shape is always an outcome of the loop, never a pre-assigned template.

0. **Derive, don't copy.** The lesson's section set and structure come from the pedagogical principle and its place in the course — never from an existing lesson file (HARNESS RULE 1); existing pages are outputs, not templates.
1. **Pedagogical assessment.** Decide what the block teaches, how central it is, and where it sits in the course (the earlier, the shorter and simpler the phrases must stay). → PEDAGOGY.md.
2. **Initial generation.** Write the items — questions, phrases, vocabulary, dialogue lines — driven by PEDAGOGY and the vocabulary guideline (VOCABULARY.md: concept → context → mapping, spoken-frequency order, all/most equivalents): the concept's weight and type decide what and how much is taught. No items-per-block or quantity-per-section target applies here, and no fill-the-width — that is a step-4/5 concern, applied only after the content is generated and inspected.
3. **Structural analysis.** Look at the block in its surroundings and decide its layout and whether more content is needed, specifically:
   - a lone item leaves a lot of blank space on its horizontal line → add items or columns;
   - a block has no adjacent block of the same width to sit beside → generate more content (more items, more columns, longer phrases, more dialogue lines) so it genuinely earns its width — or, only if pedagogy insists it stay small, keep it small and center it;
   - a block's content fills well under ~30% of its width → generate more content in the block's natural shape: more items, more columns (item grids), or more dialogue/example lines (prose such as dialogues);
   - a full-width block whose content is less than half-width → A) reduce it to a half-width block, B) restructure the content to fill the width, or C) generate more content to fill the other side — as appropriate; a full-width block whose content is more than half-width but leaves significant dead space → A) reword/regenerate the content so it becomes less than half-width, or B) restructure to fill the width, or C) generate more content to fill the other side; a deliberate half-width block (paired, or centered alone) is always fine, and pedagogical presentation takes priority over reducing width just to force a pair;
   - a multiple-choice / listening group whose stem+options row is too wide for half a panel → make it FULL-WIDTH (its inline row must actually fit);
   - two adjacent half-width blocks of visibly different HEIGHTS → when it can be done with real teaching content (never filler), extend the shorter one during step 4 so the pair is reasonably aligned — this is about the rendered HEIGHT of the blocks, never about matching item counts (two blocks can have different item counts yet match in height, or the same count yet differ); a GENERAL rule for any block type or section;
   - a prose line ends in a dangling fragment (a stray word, punctuation, or a split pair) → reword so the line ends complete (a lone label or sub-heading is fine).
4. **Alter / extend.** Generate the extra content step 3 called for, chosen for teaching value — never filler.
5. **Re-check (structural pass).** Re-run the overflow harness (`node qa/overflow.mjs <lesson>`) and confirm the step-3 goals are met — no overflow, no lone or balloon panel, no big dead space (full or half), balanced half-pair heights. Separately, read the prose for anything a measurement cannot catch (a dangling fragment, an awkward break) and log it for the owner's live-site review. If not, repeat steps 4–5. Five consecutive failures on one block: log it as an open problem, move to the next block or page, and report all logged problems at the end for the owner.
   **Per-block checklist — do not call a block done until every box is checked:** (a) exactly one defensible answer (no two-option ambiguity); (b) it tests the section's actual skill, not a proxy; (c) it fills its width — no staggered right-justified grid with short prompts, no 2-column sentence block under ~⅔ fill; (d) an adjacent half-width pair is height-balanced; (e) no overflow (panel or cell); (f) every phrase is natural and grammatical; (g) the answer is never shown in the prompt. This pass is deliberately slow — spend the extra time; a missed ambiguity or dead-space block means the pass failed.

A reported issue is a CLASS, not a single case: when the owner flags one block (e.g. "not centered"), understand the intent; when execution is requested, the step 4–5 pass sweeps and resolves that SAME issue in every block within the requested scope — never just the named one.

Pedagogical fit outranks space-filling at every step: if the right presentation is a single short column, keep it that way and make the spacing work around it.

### Content quantity
- **Explanatory content (everything before the quiz)** targets **~60 minutes of pre-quiz content** (explanatory sections + Treino combined) — a strong preference, better to exceed than undershoot. This comes from deep synthesis, never padding: conceptually hard topics get more explanation; conceptually simple topics get more practice. No fixed section count and no fixed length per section.
- **Exercise shapes** (fill-in blanks, multiple-choice, translation boxes, recording prompts, dialogues, charts…) are each used **as many times as appropriate** — never exactly one per page unless the lesson genuinely needs only one. There is no one-translation-box or one-recording-prompt rule.
- **Content type decides how a lesson grows.** A grammar rule is expanded with more production reps (not more explanation); vocabulary is expanded with more items; formulaic chunks with a larger bank; discourse with longer texts. A lesson may also contract, combine, or expand — by item quantity or by concept quantity — as its objectives require.
- **The quiz** is sized so it **ideally takes about 20 minutes** to complete, but the priority for quantity is **"as appropriate"** — enough to fully test the student's understanding of the explanatory content, no more and no less.
- **The lesson title (h1)** is centered and kept to roughly one short line — ≈ 50 characters or fewer at the fixed 38px heading size inside the 1200px content area (shorter when uppercase-heavy).

### Content shape (authoring rules)
- **Required prepositions are marked.** A verb that takes a fixed preposition (look AT, go TO, give TO, depend ON, wait FOR) is introduced with that preposition attached and visually marked (accent color + bold) so the verb+preposition reads as one unit. Never present a bare verb when it requires a preposition.
- **Explain the WHY of a split concept.** A distinction taught only as a table of examples (at/on/in for time, take/bring, say/tell) must also carry prose that explains the reason behind the choice — the mental model (at = a point; on = a day/surface; in = a period/container) — and compares it with the word's other uses. Examples alone don't teach generation.
- **Minimum lesson quantity.** A lesson must be substantial: enough teaching AND enough varied practice (a full Treino with several blocks and a full Quiz) to actually teach and consolidate the concept. A lesson that comes out with only a couple of thin sections and a short Treino/Quiz is under-built — extend it with real teaching and practice, never filler.
- **Never show the answer in a prompt.** A fill-in prompt may carry a hint ONLY in the language the student is not producing; the answer itself is never written into the prompt. If a parenthetical would reveal the answer (e.g. a Portuguese meaning that is exactly what the student writes), restructure the exercise so the prompt is one language and the student produces the other.
- **No copy-exercises.** A fill-in whose answer is already visible or derivable by simply copying the prompt (e.g. "get + up = ___" → "get up") is not a real exercise — the student must produce from memory or meaning. Restructure it into production (context sentence + meaning hint → the answer).
- **One or more exercises (as appropriate) test each skill or concept taught in the lesson, supplying its deciding condition.** Where a concept is decided by context (e.g. direction picks *bring* vs *take*), each item must carry that deciding context — a bare gloss that could go either way reintroduces the ambiguity the lesson removed.
- **Multiple-choice answers are randomized.** Across a group, the correct option is spread over positions a/b/c/d — never all the first option.
- **Treino and Quiz stay distinct.** A Treino block and its Quiz counterpart test the same skill but never reuse the same phrases, objects or contexts — if both reuse a block type (fill-in, listen-and-choose, translate), the items must still differ (see the no-redundancy rule).
- **Quiz/Treino blocks are sanity-checked against the lesson's level and content type.** Every block's exercise TYPE must fit both the skill being tested and the student's place in the course — a recognition task that is trivial at a later lesson, or a production task too hard at an early one, is a failed block. Vary the exercise types within and across lessons (fill-in, choose, reorder, dictation, transformation, translation, record…) instead of repeating one or two shapes through a whole quiz or stage.
- **Listen-and-choose phases out after lesson 7.** Listen-and-select blocks train the ear for early recognition; from lesson 8 on, replace them with dictation (hear a sentence and type it) or another production/higher-order listening task — never another recognition grid. A later listen-and-choose is justified only when a specific item genuinely needs pure recognition.
- **Explainers vs notes.** A one-liner that explains a whole section is a sub-heading (serif, slightly larger), written only when it adds what the chart/dialog does not already state. A note about a single item (one vocab row) is a merged row inside that block, directly under the item.
- **No redundancy (strict).** Never repeat the same noun, object or phrase across the items of one block, and never reuse an item's noun/object/phrase from a Treino block in its Quiz counterpart — the quiz tests the same skill with different sentences and objects. Also never restate in prose what the very next chart already shows, and never repeat a block's title twice (a section heading plus the block's own sub-title). State each thing once; a repeated noun/object/phrase is a failed pass, not a style choice.
- **Contrast is visible.** Two versions/conjugations/uses of a concept, or two concepts, are always separated — columns or clear spacing.
- **A false friend is taught as a trio.** For every false friend, show three things: the English word, its real meaning, and the correct English for the Portuguese word the student actually meant — so the intended concept is never lost.
- **Teach the pattern — or state there is none.** For every concept, determine (by research/reasoning) whether a pattern, regularity or logic exists and is worth teaching; teach it when it does, and say so explicitly when it does not (e.g. there is no rule predicting which phrasal verbs separate — it is a per-verb property), so the student knows what to memorize vs. derive.
- **A rule and its direct consequence stay together.** Two sections that are one concept (a rule and its consequence, e.g. separability → pronoun position) stay in ONE section with an explicit bridge ("Consequência:"), or are cross-referenced — never split without explaining how they relate.
- **A context vehicle that leans on new items comes after they are taught.** A story, dialogue or scenario that leans heavily on items the student has not met yet comes AFTER those items are taught, so it is comprehensible and consolidates what was just learned. If it must come first, the new items must be presented within the vehicle/section in some way (primarily core notes; other presentation methods remain available) — or the vehicle uses only already-known items.
- **Carrier phrases match the lesson's expected level.** Every example phrase, context and exercise prompt escalates with the course — later lessons draw on all prior vocabulary and structures and use longer, more complex, more business-register sentences; an advanced lesson never falls back to beginner phrasing.
- **Choose the natural input.** "word → answer" facts (e.g. person → people) are fill-in text fields; recognition / "pick the right one" is multiple choice.
- **Blanks are contiguous lines** (the input.gap), never literal "___" underscores in the prompt.
- **Right-justified fill-in grids stagger with short prompts.** A multi-column fill-in grid right-justifies each cell (CSS `justify-content:flex-end`), so short prompts leave dead space to the left of each cell and between columns. For short-prompt fills use the aligned layout (prompt | field | after) or sentence fill-ins; keep the plain multi-column grid for prompts long enough that the grid reads as intentional.
- **Fill the width (judgment, not a count).** Generate enough content that each block fills its width with no dead space; the number of items follows from what fills the layout, not from a fixed count (4 and 8 are only illustrations of a full grid). Add or trim by pedagogical value (see PEDAGOGY), never by padding with filler.
- **Options are authored to fit their line — never wrapped by CSS.** Short options sit on one line; long options (whole sentences, as in translation or listening) are laid out stacked under the stem. Inline is only correct when the whole stem+options row fits the block's width — a group whose row is too wide for half a panel is made FULL-WIDTH, never squeezed into half-width. The page never relies on CSS text wrapping to squeeze over-long options into a row.
- **Listening items stay inline.** In a listen-and-choose item the ▶ button and the answer options sit on the same line — an audio-only stem is never stacked, because a lone ▶ above the options looks broken. A listening group is a full-width block, and its options are authored short enough to fit that one line.
- **Recording prompts carry only their text — and no blanks.** A ⏺ recording block shows only the sentence(s) to record — the header already names the activity ("F. Grave ⏺"), so the body does not repeat "Grave", and it never says "record line N of the dialogue". The sentence is complete and read-aloud-able: it never contains a fill-in blank (___); a blank is filled with a concrete name, city, place or brand as appropriate.
- **No repeated labels.** A block whose header already names the activity (e.g. "F. Grave ⏺", "Diálogo — leia em voz alta") does not repeat that wording in its body or a nested title.
- **Small half-full blocks are centered.** When a small block's text leaves its right half empty, center the text — judged case-by-case in the structural pass (ugliness), not as a blanket rule.
- **Nothing reads as accidental or broken.** If a line ends in a dangling fragment — a stray punctuation mark, a lone trailing word, or a split pair like "word · word" — reword so the line ends complete. A fragment is fine only when it is a deliberate label or sub-heading (e.g. "Consequências:") that introduces what follows. The test: does it read as deliberate, or does it read like the text broke?
