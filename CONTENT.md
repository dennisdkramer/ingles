# CONTENT — content-handling contract: how lesson content is handled, structured and generated
This file does NOT hold lesson content — the prose, sections, exercises and widgets of a lesson live in that lesson's OWN HTML page file. This file holds the CONTENT HANDLER/ARCHITECTURE (where content lives, how it is structured and generated); guidance ABOUT the content and ideas FOR generating content are welcome here. Layout/styling → FORMAT.md · behaviour → FUNCTION.md (Backend section) · teaching side → PEDAGOGY.md.

## CONTENT MAP
- Lesson pages are content-only: config consts + the engine includes (see FUNCTION.md); every lesson's prose, sections, exercises and widgets live in the page file itself.
- **Fixed page skeleton vs. derived content.** The only mandatory page parts are the mechanical skeleton: doctype/head/title/stylesheet, #toast, header.brand, #controlbar, main#page → .page-container → .content-area, the centered h1, the footer, the closing script block (BACKPACK/SECRET/TRACK/L/COUNT + engine1.js/engine2.js + the engine-load guard), and the #feed (shared notebook) box, which the harness requires. (The #trw translation textarea is NOT part of the skeleton — it is a reusable exercise shape, included only when a translation exercise is pedagogically needed.) Everything else — every section (including any opening "abertura"), block and exercise group — is derived content, generated from the pedagogical principle and included only if it earns its place. A lesson's quiz is the customary final check; its contents are whatever tests the lesson. Site-usage instructions (highlight/note/record gestures) are not lesson content — they live in the control bar (ISSUES B-I9).
- Tracks: kids/ · business/ · nsfw/ — each lesson is a standalone page; business/lesson1.html–lesson34.html are the current build (a single 34-lesson progression). (Each lesson has a `<lesson>.edit.html` sidecar — see FUNCTION.md Edit mode.)
- A translation textarea (the `#trw`-style box) is the student's own written work and is persisted like every other exercise input. It is a REUSABLE exercise shape, not a fixed one-per-page slot: a lesson includes as many as appropriate, in Treino and/or Quiz.
- Exercise layout — STANDARDS (fallbacks; mechanism in style.css): the established presentation is a bordered panel inside a two-per-row flow (a group that needs full width can span the whole row). Two established shapes are the fallback: (1) multiple-choice — an aligned grid of [number][stem][one column per option] so options line up vertically; (2) fill-in — an auto-flowing grid where the prompt sits in a fixed-width column so gaps line up, letting the number of pairs per row fall where it fits the item width. These are standards, not a closed set — a creative pass may depart from them, and a new exercise shape is recorded in FORMAT.md when introduced. A page never hand-tunes columns; column behaviour is an outcome, not a preset.
- **Pronunciation content types (first introduced in business/lesson12).** Sound-teaching blocks that all reuse existing components (`.chart` tables, `.grid3` cards, `.qgrid.stack` MCQ, `.blanks.sent` dictation/fill-in, `.listen` chips, ⏺ recording): (1) *pronunciation lab* — a mouth-position guide (articulation, in PT) paired with a *PT-vs-EN contrast table* ("you say X → say Y"); (2) *minimal-pairs grid/table* — the target word beside its near-neighbours with audio (think/sink/fink; three/tree/free), plus homophone pairs from the flap T (ladder/latter) and silent letters (know/no); (3) *listen-and-identify* — "which TH? / which T?"; (4) *error-correction* — "which is correct?" (at whatever granularity fits the lesson — single words or whole sentences); (5) *progressive multi-step drill* — one block in three labelled steps (identify → discriminate → produce); (6) *tongue twisters + echo/shadowing* — production of connected speech. No new CSS was required; future reuse needs none.
- **Two-level key + reductions (business/lesson13–14).** `data-pron="word"` renders the careful L1 (schwa shown) and `data-pron="word:2"` renders the natural L2 (schwa dropped, fewer syllables) — introduced and trained in lesson 13 as a side-by-side table, then applied to reduction pairs in lesson 14 (have→'ve→'a, and→'n, going to→gonna, would have→woulda). New words are added to the dictionary FIRST (engine2.js `PRON`), before authoring. New exercise shapes on top of the existing components: syllable-counting, stress-locating, schwa-hunting, "which word shrinks?", reduction fill-in/error-correction, and a connected-speech sentence dissected across lessons 12–14. Still no new CSS.
- Edit mode (teacher-only) is FUNCTIONALITY, not content handling — it lives in FUNCTION.md (Edit mode).

## Pedagogical guidance — WHAT to teach and its order

### Lesson synthesis (before generating any block)
Each lesson is a deep, thorough pedagogical synthesis — never a template fill-in and never a copy of a neighboring lesson's structure. A lesson's content, concept, section structure, block/activity type, wording and examples are all generated FROM SCRATCH each time, chosen solely by what the pedagogy for that concept needs — conceived in a VACUUM, without referencing any existing lesson, block, exercise shape or formatting in this project. Presentation is a SEPARATE step that comes AFTER: first decide WHAT to teach and why, then decide (or invent) how to present it. Previous/other lessons are consulted ONLY to (a) establish what the student already controls and what comes next, and (b) as a last-resort fallback for ideas or structure when genuinely stuck — and even then they are read for the PRINCIPLE and interpreted broadly, never mined for specific parts, wording, blocks or structures to reuse. (The one fixed exception is the mechanical page skeleton — CONTENT.md — which is reproduced by rule.) Start from the pedagogical principle, situate it against the content of the other lessons (what the student already knows and what comes next), and — whenever possible — research several outside sources on the lesson's topic to brainstorm ideas, not to copy. Before authoring a single block: (1) decide what the student must already understand (prerequisites) and teach it first; (2) choose the cleanest concept order (concrete/transparent → abstract/idiomatic); (3) decide the appropriate SET and QUANTITY of items — enough to build the system, never a fixed count; (4) plan how each item is presented (meaning/use, register, context, required prepositions attached); (5) plan enough practice to build comfort and intuition, then the quiz. Research and reason about the topic; owner-named items are pointers, not deliverables (HARNESS RULE 1). Make structural changes — add, remove or reorder columns, blocks and sections — whenever the pedagogy warrants it; the block template is a starting point, not a constraint.

## Generative guidance — HOW to generate, structure, format

**Default — be creative.** Freely imagine; content type, layout and format are flexible, chosen by this priority: (1) pedagogical clarity, completeness and difficulty as the lesson's concepts require → (2) student-engagement potential → (3) professional-looking results (alignment/spacing) → (4) no dead space (use width and "generate more content to fill" where needed). The established content types and format details are STANDARDS (fallbacks) — followed when the prompt or task requires compliance with them, or does not request creativity — not a menu to pick from by default.

**Two kinds of guidance below.** (1) GENERAL principles — apply to ALL content, whatever is generated: nothing reads as accidental or broken, exactly one defensible answer, the answer never shown in the prompt. (2) COMPONENT standards — the established formatting for a specific element (a chart, a multiple-choice group, a dictation, a recording, …), applied when that element appears in standard/compliance mode; a creative pass may use them or depart from them.

### Content generation process (every block)
**Initiation.** Initiating teaching-content generation triggers — while conforming to the prompt and not conflicting with it — scoped brainstorming, pedagogical analysis, difficulty-level analysis, and planning of presentation & content types.
Content is produced by a loop; layout is never pre-assigned and never forced by CSS — a block BECOMES full-width, half-width, one column or several columns as a RESULT of this loop.

**Default:** if prompt allows, a content-generation request implicitly includes the whole loop — steps 4 and 5 (alter/extend + structural re-check) are ALWAYS run afterward, unless the owner explicitly directs otherwise. Running only the generation pass (and skipping the 4–5 pass) is not "done".

**Intent notes.** "look at / take a look at" a block or page means READ and REASON about its HTML/content — never render or screenshot it (the agent has no vision). A short target label ("6A", "5.6A", "block A") that could point at more than one lesson/section/block must be clarified before acting, never guessed (see HARNESS.md RULE 1).

**Malleability.** There are no fixed shapes for activities or blocks, and no fixed exercise types per lesson. Layout is flexible (see the default priority above): a block's shape — a chart, a panel, a dialogue, a fill-in grid, a wide sentence-length field — is chosen during the step-3/4/5 pass to fit the content and the structural result. The established shapes are standards (fallbacks) used in compliance mode, never a pre-assigned template.

0. **Derive, don't copy.** The lesson's section set and structure come from the pedagogical principle and its place in the course — never from an existing lesson file (HARNESS RULE 1); existing pages are outputs, not templates.
1. **Pedagogical assessment.** Decide what the block teaches, how central it is, and where it sits in the course (the earlier, the shorter and simpler the phrases must stay). → PEDAGOGY.md.
2. **Initial generation.** Write the items — questions, phrases, vocabulary, dialogue lines — driven by PEDAGOGY and the vocabulary guideline (VOCABULARY.md: concept → context → mapping, spoken-frequency order, all/most equivalents): the concept's weight and type decide what and how much is taught. No items-per-block or quantity-per-section target applies here, and no fill-the-width — that is a step-4/5 concern, applied only after the content is generated and inspected.
3. **Structural analysis.** Look at the block in its surroundings and decide — by judgment, not a template — whether its layout serves it and whether more content is needed. Layout is chosen freely to fit the content; the only hard requirement is a clean result in step 5. Techniques you MAY use (each optional, only when it helps):
   - a lone item leaving blank space on its line → you can add items or let them flow into more columns;
   - a block with no same-width neighbour → you can generate more content so it fills, or — only if pedagogy insists it stay small — keep it small and center it;
   - a block whose content fills only a sliver of its width → you can generate more content in its natural shape (more items, more columns, more dialogue/example lines);
   - a full-width block whose content reads as sparse → you can reduce it to a narrower block, restructure the content to fill, or generate more content beside it; a deliberate narrower block (paired, or centered alone) is always fine, and pedagogical presentation outranks width;
   - a multiple-choice / listening group whose stem+options row is too wide for the space → you can widen the block so its row fits;
   - two adjacent blocks of visibly different heights → you can extend the shorter with real teaching content (never filler) if alignment matters here;
   - a prose line ending in a dangling fragment → reword so the line ends complete.
4. **Alter / extend.** Generate any extra content step 3 called for, chosen for teaching value — never filler.
5. **Re-check (structural pass).** Re-run the overflow harness (`node qa/overflow.mjs <lesson>`) and confirm the result is clean — no overflow, no lone or balloon panel, no big dead space, no awkward prose that a measurement cannot catch (a dangling fragment, an awkward break); log anything remaining for the owner's live-site review. If not clean, repeat steps 4–5. Five consecutive failures on one block: log it as an open problem, move on, and report all logged problems at the end for the owner.
   **Per-block checklist — do not call a block done until every box is checked:** (a) exactly one defensible answer (no ambiguity); (b) it tests the section's actual skill, not a proxy; (c) it reads as deliberate — no accidental dead space or awkward grid; (d) no overflow (panel or cell); (e) every phrase is natural and grammatical; (f) the answer is never shown in the prompt. This pass is deliberately slow — spend the extra time; a missed ambiguity or dead-space block means the pass failed.

A reported issue is a CLASS, not a single case: when the owner flags one block (e.g. "not centered"), understand the intent; when execution is requested, the step 4–5 pass sweeps and resolves that SAME issue in every block within the requested scope — never just the named one.

Pedagogical fit outranks space-filling at every step: if the right presentation is a single short column, keep it that way and make the spacing work around it.

### Content quantity
- Each lesson robustly but concisely teaches its pedagogical concept with no quantitative limit on lesson content.
- **The lesson title (h1)** is centered and kept to roughly one short line — ≈ 50 characters or fewer at the fixed 38px heading size inside the 1200px content area (shorter when uppercase-heavy).

### Content shape (authoring rules)
- **Explain the WHY of a split concept.** A distinction taught only as a table of examples (at/on/in for time, take/bring, say/tell) must also carry prose that explains the reason behind the choice — the mental model (at = a point; on = a day/surface; in = a period/container) — and compares it with the word's other uses. Examples alone don't teach generation.
- **Never show the answer in a prompt.** A fill-in prompt may carry a hint ONLY in the language the student is not producing; the answer itself is never written into the prompt. If a parenthetical would reveal the answer (e.g. a Portuguese meaning that is exactly what the student writes), restructure the exercise so the prompt is one language and the student produces the other.
- **No copy-exercises.** A fill-in whose answer is already visible or derivable by simply copying the prompt (e.g. "get + up = ___" → "get up") is not a real exercise — the student must produce from memory or meaning. Restructure it into production (context sentence + meaning hint → the answer).
- **Pre-quiz placement is free; Treino stays training-only.** Any pre-quiz content type, component or block may appear in any pre-training (teaching) section, in any order, for any pedagogically defensible reason. The training (Treino) section remains limited to training content — content that practises the concepts, vocabulary or skills.
- **Coverage: train 75%+, then test 75%+.** At least 75% of the concepts, vocabulary or skills covered by the lesson are trained by training content — placed either directly after the concept/vocabulary/skill it trains, or in the training (Treino) section — and the same percentage is subsequently tested in the quiz, with independently chosen content types and independently generated question content that does not reference or build on the training content.
- **Each item supplies its deciding condition.** Where a concept is decided by context (e.g. direction picks *bring* vs *take*), each item must carry that deciding context — a bare gloss that could go either way reintroduces the ambiguity the lesson removed.
- **Order of multiple-choice answers is shuffled** to randomize correct-answer position — the correct option is not always in the same slot within a group.
- **Treino and Quiz stay distinct.** A Treino block and its Quiz counterpart test the same skill but never reuse the same phrases, objects or contexts without pedagogical motive — even when both use a similar shape, the items must still differ (see the no-redundancy rule).
- **Quiz/Treino blocks are sanity-checked against the lesson's level.** Every block's exercise type must fit both the skill being tested and the student's place in the course — a recognition task that is trivial at a later lesson, or a production task too hard at an early one, is a failed block.
- **Explainers vs notes.** A one-liner that explains a whole section is a sub-heading (serif, slightly larger), written only when it adds what the chart/dialog does not already state. A note about a single item (one vocab row) is a merged row inside that block, directly under the item.
### General principles — apply to ALL content
- **No redundancy without pedagogical motive.** Never repeat the same noun, object or phrase across the items of one block, and never reuse an item's noun/object/phrase from a Treino block in its Quiz counterpart — the quiz tests the same skill with different sentences and objects. Also never restate in prose what the very next chart already shows, and never repeat a block's title twice (a section heading plus the block's own sub-title). State each thing once; a repeated noun/object/phrase is a failed pass, not a style choice.
- **Contrast is visible.** Two versions/conjugations/uses of a concept, or two concepts, are always separated — columns or clear spacing.
- **A false friend is taught as a trio.** For every false friend, show three things: the English word, its real meaning, and the correct English for the Portuguese word the student actually meant — so the intended concept is never lost.
- **Teach the pattern — or state there is none.** For every concept, determine (by research/reasoning) whether a pattern, regularity or logic exists and is worth teaching; teach it when it does, and say so explicitly when it does not (e.g. there is no rule predicting which phrasal verbs separate — it is a per-verb property), so the student knows what to memorize vs. derive.
- **A rule and its direct consequence stay together.** Two sections that are one concept (a rule and its consequence, e.g. separability → pronoun position) stay in ONE section with an explicit bridge ("Consequência:"), or are cross-referenced — never split without explaining how they relate.
- **A context vehicle that leans on new items comes after they are taught.** A story, dialogue or scenario that leans heavily on items the student has not met yet comes AFTER those items are taught, so it is comprehensible and consolidates what was just learned. If it must come first, the new items must be presented within the vehicle/section in some way (primarily core notes; other presentation methods remain available) — or the vehicle uses only already-known items.
- **Carrier phrases match the lesson's expected level.** Every example phrase, context and exercise prompt escalates with the course — later lessons draw on all prior vocabulary and structures and use longer, more complex, more business-register sentences; an advanced lesson never falls back to beginner phrasing.
- **Nothing reads as accidental or broken.** If a line ends in a dangling fragment — a stray punctuation mark, a lone trailing word, or a split pair like "word · word" — reword so the line ends complete. A fragment is fine only when it is a deliberate label or sub-heading (e.g. "Consequências:") that introduces what follows. The test: does it read as deliberate, or does it read like the text broke?
- **All tracks conform to prevalent spoken English.** Nothing is avoided because it is informal or technically incorrect (e.g. gonna, gotta).

### Component standards — the established formatting, applied when the element appears in standard/compliance mode
- **Blanks are contiguous lines** (the input.gap), never literal "___" underscores in the prompt — this is what the answer-saving engine reads.
- **Fill-in grids.** In a multi-column fill-in grid a short prompt can leave dead space; the established fixes are a right-justified cell, the aligned layout (prompt | field | after), or sentence fill-ins.
- **Options are authored to fit their line — never wrapped by CSS.** Short options CAN sit on one line; long options (whole sentences) CAN be stacked under the stem. Inline works only when the whole stem+options row fits the block's width — otherwise widen the block. The page never relies on CSS text wrapping to squeeze over-long options into a row.
- **Listening items.** In a listen-and-choose item the ▶ button and the answer options CAN sit on the same line (an audio-only stem stacked above options can look broken) — choose the layout that reads best.
- **Recording prompts.** A ⏺ recording block shows the sentence(s) to record — the header already names the activity, so the body does not repeat it, and the sentence is complete and read-aloud-able (no fill-in blanks).

### Exercise-type catalog (options — generation & persistence)
Answers persist only through three input kinds — `input.gap` (fill-in), `input[type=radio]` (single-select), and a non-feed `textarea` (free text/translation) — see FUNCTION.md. Author any exercise shape onto one of these three so its answers save; a shape needing a different input (checkbox, `<select>`, drag/drop) is display-only unless the engine is extended. Shapes you may use (a brainstorm — none is required):

- **Multiple choice (radio).** One correct answer among 2–5 options; the audio-stem variant is listen-and-choose (▶ + radio). Persists via `radio`.
- **Fill-in blank / cloze.** One or several `input.gap` in a sentence or short passage. Persists via `input.gap`.
- **Dictation / transcription.** Hear ▶ and type the word or sentence. Persists via `input.gap` (word) or `textarea` (sentence).
- **Free text / translation.** Open written answer in a `textarea` (or `#trw`). Persists via `textarea`.
- **Reorder / unscramble.** Student rebuilds a sentence; author it as a gap/textarea (type the reordered sentence) so it persists — a draggable-chip UI is display-only.
- **Matching / pairs.** Two columns to pair; author as one radio row per item (each row selects its match). Persists via `radio`; `<select>`/drag is display-only.
- **Categorization / sort-into-groups.** One radio per item (pick the group). Persists via `radio`.
- **Error correction (find & fix).** Student rewrites the corrected form in a `textarea`. Persists via `textarea`.
- **Transformation / rephrase.** Rewrite in a `textarea`. Persists via `textarea`.
- **Odd-one-out.** Pick the item that doesn't belong. Persists via `radio`.
- **True/false · yes/no.** Two-option `radio`. Persists via `radio`.
- **Ordering / ranking.** Type the sequence into a gap/textarea; a drag UI is display-only.
- **Multi-select (checkboxes).** Not persisted by the current engine — avoid for scored answers, or wire a new input type first.
- **Production / recording (⏺).** Read aloud and record; the output is the recording mark itself (persisted as a recording, not an answer row).
