## Cross-feature principles (owner prompt 2026-10-13 — OVERRIDES any conflicting wording below)
Shared by Highlight, Note and Recording; the per-feature within/overlap/contain rules in each section below remain in force.
- SHARING: the three may share elements/subfunctions IF AND ONLY IF the behaviour is identical and the sharing causes no conflict or interaction between them. A shared skeleton is fine; any type-specific divergence is isolated by type and never leaks across features. Note and Recording share the one save and the one delete core — the shared part is identical and the recording-only Drive upload/purge is a type-isolated branch, so sharing is safe. Highlight does NOT share those save/delete cores: its within/overlap/contain logic is subtract-never-merge, so sharing them would risk conflict. All three share only the behaviour-identical, generic infrastructure — the network write, the id+action grace window, and the block-boundary predicate.
- SEPARATE IDENTITY: the reference strings and files each feature creates are SAVED, CHECKED and DELETED separately. "Checked separately" means each is its OWN row/identity, looked up and resolved as a DISTINCT item — never merged into one row. It does NOT require separate lookup functions: the popup may resolve the note and the recording in one pass (the "same popup" rule requires them together) and still treat them as two independent items.
- VISUAL OVERLAP, NO DATA INTERACTION: they may overlap visually with no conflict and no interaction at the DATA level — a note's row, string or saved content is never altered by a recording, and vice versa. Their marks are SEPARATE visual elements, each carrying only its own identity; when they cover overlapping text they may overlap visually, which is a layout artifact, NOT a data interaction. The ONLY intentional interaction is that a clicked text string or a text selection referencing BOTH a note and a recording shows — and enables interaction with — BOTH through the SAME popup.
- ABUTTING, SAME TYPE: an abutting selection/save of the SAME type has NO interaction with the existing one; the new one is saved separately (its own row). Merely touching (a.end === b.start) is never an overlap.
- HIGHLIGHT within/overlap/contain logic (subtract, never merge) and the colour-change behaviour are MAINTAINED UNCHANGED — see the Highlight section below.

## Highlight (text range) — owner spec 2026-10-11, mouse-release gate updated 2026-10-12
- Gesture: Ctrl must be held at MOUSEDOWN over the selection; if Ctrl is ALSO held at MOUSEUP, that release creates the highlight. Nothing else creates one (no keyboard-only path, no touch gesture, no automatic path).
- Ctrl at mousedown SUPPRESSES the other selection-based functions for the whole gesture (and ~1.2s after it ends): the Hear / Record / Note popup never opens for a Ctrl gesture, whether or not a highlight ends up being created. A normal selection (no Ctrl at mousedown) still opens that popup exactly as before.
- MOUSE-RELEASE GATE (owner spec 2026-10-12): both functions are decided ONLY at the moment the mouse button is released on a text selection, never mid-drag. If Ctrl is held at that release → the highlight function fires (and ONLY the highlight function). If Ctrl is NOT held at that release → the Hear/Record/Note popup fires (and ONLY that popup). A debounced selectionchange still exists as a fallback for non-mouse selection changes (keyboard Shift+Arrow, touch), but while a mouse button is physically down neither function may open.
- Highlight visuals sit BELOW the text ink (`mix-blend-mode:multiply` on `.hlr`): black glyphs stay pure black, the tint only shows through the paper/background underneath.
- Ctrl+click ON a painted highlight = delete it. One action: no confirmation, no popup. That deletion is the ONLY interaction a highlight has.
- A highlight never makes the text clickable and never changes mouseover or the cursor: no click behaviour of its own (a plain click on highlighted text does nothing) and no hover state.
- Ctrl+drag over an existing highlight SUBTRACTS, NEVER MERGES (owner spec 2026-10-12): the new highlight keeps its WHOLE selection and every character it covers is REMOVED from the highlight(s) already sitting on it, so a second highlight can carry a DIFFERENT colour over text that was already highlighted. The old rule did the opposite — it unioned both ranges into ONE row with ONE colour, which is exactly what destroyed the second colour. What survives of an older highlight keeps its own colour and only shrinks: partly covered → one piece on the SAME row (a `set` with the shorter anchor); the new range strictly inside it → the highlight is SPLIT in two (the first piece keeps the row, the second is a new row, an `add`); fully covered → no character left, its row is `del`eted. Nothing is ever extended to cover an older highlight (no union). A highlight that merely TOUCHES the new range (old.end === new start) shares no character with it and is left untouched, so two same-colour highlights may sit side by side (the seam between them is fine — owner's call). A whitespace-only piece is never painted, and the trim only runs after the selection passed the usual validation (a whitespace-only selection never deletes anything). Notes and recordings are never merged, extended, moved or recoloured by a highlight gesture.
- LAYER SEPARATION (owner rule, rework #2): highlights are PAINTED ON THEIR OWN LAYER — translucent coloured rectangles measured from the text range. A highlight is therefore NOT an element of the text at all; the text belongs to the note/recording marks alone. Consequence: a highlight may intersect or cross a note/recording in ANY way and both stay whole — nothing is ever refused, split, cloned, moved, hidden or suppressed in either direction, and creating or deleting one never changes the other. The highlight layer never blocks a click, a drag or a text selection, and creates no stacking context (it stays below the popup and the toast).
- Anchor: the highlighted STRING is the reference; the stored (block index, character offset) is only a TIE-BREAKER that picks between two identical occurrences of that string — text identifies the item, position only discriminates between identical candidates, never the other way round (owner spec 2026-10-13). The offsets also keep the highlight's place across resize, zoom, font changes and reflow; if the string no longer matches (page edited) it falls back to the anchor text alone, then to nothing.
- The layer may be re-measured (reflow) at any time: window resize/zoom, web-font load, `<details>` open/close and any mouseup repaint the rectangles from the anchors.
- It may span several lines of the same block (paragraph, list item, cell, heading) but never crosses a block boundary (refused with a toast).
- Look: semi-transparent yellow fill that keeps the text readable, rounded ends on every line fragment, no border, no icon.
- After a highlight is created, a tiny colour palette pops above the LAST painted rectangle with three swatches: yellow / transparent red / transparent green. Clicking a swatch recolours the highlight and closes the palette; any click elsewhere closes it too, and so does any other key press. Ctrl and Meta are the exception and never close it: the palette is born while the gesture's own Ctrl is still held down, so that key's keydown (including the auto-repeat the keyboard keeps sending while it stays held) must not close the popup the gesture just opened.
- Coexistence: recording (green underline) and note (very light blue wash) — neither carries a trailing 🎙/📝 icon any more — and the highlight are three separate layers; all three can cover the same span and none of them replaces or triggers another.
- PC only: highlights have no touch gesture.
- Persistence: server row type "hl", anchor = the highlighted string, data = {"color":"yellow|red|green","b":<block index>,"o":<char offset>}; a recolour is a "set" on the same id. Old rows without b/o still restore by anchor text. No backend change needed (add/set/del already accept any type). An overlap is persisted as the SUBTRACTED pieces (owner spec 2026-10-12): the surviving piece stays on the SAME row via a "set" (shorter anchor + offsets), a split's second piece is an "add" with a fresh id, a fully covered highlight is "del"eted — the same three actions, still no backend change.
- DOM contract: NO highlight element exists in the page text — highlights are painted only on their own separate layer (translucent coloured rectangles). Notes and recordings are their own separate elements. The element sets are never mixed and never nest.

  - A selection that is INSIDE, OVERLAPS or CONTAINS an existing RECORDING (an audio file) LOCKS ⏺ Record — RE-RECORDING IS NO LONGER POSSIBLE (owner spec 2026-10-12 #2), and that includes covering the recording EXACTLY. A selection that merely ABUTS a recording (shares no character with it) is an ordinary new phrase and records normally.

## Sync (cross-session push) — owner spec 2026-10-12
- The ONLY re-check mechanism is a plain poll: `setInterval(loadLayer,3000)` in engine2.js. There is no per-action immediate reload any more (the old `setTimeout(loadLayer,1800)` after every send() is gone) — every add/set/del on either side (teacher or student) reaches the other session within one poll cycle (~3s), not instantly.
- GENERIC GRACE WINDOW: every call to `send(o)` marks `o.id`+`o.action` as "pending" for 12s (`notePending`/`pendingFor` in engine1.js). `renderLayer()` in engine2.js skips re-applying (reverting or resurrecting) any row whose id still has a pending local action — the UI already applied that action directly when the user acted, so a poll snapshot that races ahead of the backend write is simply ignored for that id until the pending window elapses or a later poll confirms the server agrees.
- This mechanism is GENERIC by id+action, not hard-coded per feature (highlight add/color/delete, note add/delete, recording add/delete today) — any future action type routed through `send()` is automatically protected from the same revert-then-reapply flicker with zero additional code. The note/recording layer uses the same window: `nbAnyPending` keeps a freshly created/edited/deleted mark exactly as the click left it until the window elapses.
- THE ROW ITSELF SURVIVES THE POLL, not just the mark (owner report 2026-10-12: a saved note vanished from the phrase and from the popup until the server confirmed the write). `renderLayer` skips a stale ROW, but the poll replaces the whole `layer` with the server snapshot, and every reader of the note/recording layer (the popup's note text `nbNoteText`, ▶ Play's row lookup, `nbHasNote`/`nbHasRec`) reads exactly that row — so a snapshot fetched before the backend write landed made the note disappear for a whole poll cycle. The ONE core save `nbUpsert` therefore also keeps its local copy of the row (`nbLocal`) and `nbEntries`, the single read point of that layer, serves it in place of the snapshot's absent/older copy for as long as the id's own window is open — the same treatment `hlList` gives a freshly painted highlight, using the same `notePending`/`pendingFor` window and no second timer. Notes and recordings both get it, since both save through `nbUpsert`. `pendingFor(id)` returns the MOST RECENT action queued for that id, so a row whose latest local action was a delete (`del`) is never resurrected from `nbLocal`; once the server's row is confirmed the local copy is no longer consulted, and a rejected write drops it when the window expires.
- Lessons are content-only files: config consts (TRACK, LESSON, SECRET, BACKPACK…) + engine includes; engines and style.css stay single shared files, never inlined per lesson.
- Gate hash: h(s){let x=0;for(const c of s)x=(x*31+c.charCodeAt(0))|0;return x} applied to email+track+SECRET ("abreportas2025"); invalid/missing gate → redirect to portal.html.
- Backend actions: POST add/set/del/wipe; GET ping/layer/file/dbg. ?action=dbg returns server log. EVERY recording's audio is stored in Drive (IAP_uploads) — the row's b64 column keeps only a `drive:<fileId>` pointer — and del and wipe TRASH that file via purgeDrive_ (never throws), so deleting a recording removes both the row and its audio (reply `purged:true`). (Inline b64 is a last-resort fallback only when the Drive upload itself fails and the clip fits a spreadsheet cell, <45k chars.)
- `?action=layer` returns each recording as `fileId` (Drive) OR `b64` (the inline fallback), so a clip that never reached Drive is still playable after a reload; a page refresh must never turn a saved recording into "no saved audio".

## Function-generated formatting (the elements a function creates at run time; FORMAT.md defers to this section for them)
Rule: formatting that only exists because a FUNCTION creates the element is specified here, as PART of that function — not in FORMAT.md (FUNCTION.md wins on any conflict). style.css is still the single styling source; these are its per-element specs.
- Note/Recording marks: a recording is indicated by a 2px BLUE underline (no trailing icon); a note is indicated by a very light blue wash (no trailing icon) (the wash is a painted background, so a highlight over the same span never hides it). Both are painted INSET — 1px short of the text on each side — so two ABUTTING saves leave a paper gap between them; a phrase that is both recorded and noted carries both indicators (the underline over the wash).
- Highlight layer: painted on its OWN layer (separate from any element inside the text) as translucent coloured rectangles measured from the highlighted text range; it sits below the text ink (so black glyphs stay pure black and the tint only shows through the paper), never blocks a click/drag/selection, and carries no cursor or hover change.
- Colour palette: a tiny 3-swatch palette (yellow/red/green) shown near the just-painted highlight.
- Selection popup: fixed, paper, ink border, rounded, tan shadow, max-width ~380px; small one-line English buttons. The note/recording popup always shows its seven buttons (▶ Hear / ▶ Play / ⏺ Record / 🔊 Delete / 📝 Add/Edit Note / 💾 Save / 📝 Delete); the ones that don't apply yet are greyed out — never removed. ⏺ Record is greyed-but-still-pressable as soon as ANY recording is involved (re-recording is gone — its press toasts "cannot overwrite recording, delete first"), and ▶ Play / 🔊 Delete while MORE THAN ONE recording is involved (their press toasts "please select a distinct recording"). It does NOT repeat the selected text, and a saved note is shown above the buttons as plain dark text (no blue strip, no icon). A button whose action is running (Record while recording, Play while playing) replaces its label with a spinner.
- Toast: fixed top-center pill, ink/cream. Recording indicator: shown top-center while recording. A spinner replaces the Record/Play glyph while recording / while the clip plays.
