# FUNCTION — frozen site behavior contract
Reference this file whenever a task touches lesson functionality. Preserve everything here unless the owner explicitly asks to change it.

## Persistence & identity
- ALL user data persists server-side (Apps Script Sheet "IAP_backpack!layer" + Drive "IAP_uploads"), and is separate PER STUDENT AND PER BOOK (track). No cross-contamination between students or between tracks.
- Recordings, notes, highlights, filled-in fields, answered questions: all persistent.
- localStorage must never be a source of truth (ghost-data bug of Oct 2026); server is sole source.

## Highlight (text range) — owner spec 2026-10-11, mouse-release gate updated 2026-10-12
- Gesture: Ctrl must be held at MOUSEDOWN over the selection; if Ctrl is ALSO held at MOUSEUP, that release creates the highlight. Nothing else creates one (no keyboard-only path, no touch gesture, no automatic path).
- Ctrl at mousedown SUPPRESSES the other selection-based functions for the whole gesture (and ~1.2s after it ends): the Hear / Record / Note popup never opens for a Ctrl gesture, whether or not a highlight ends up being created. A normal selection (no Ctrl at mousedown) still opens that popup exactly as before.
- MOUSE-RELEASE GATE (owner spec 2026-10-12): both functions are decided ONLY at the moment the mouse button is released on a text selection, never mid-drag. If Ctrl is held at that release → the highlight function fires (and ONLY the highlight function). If Ctrl is NOT held at that release → the Hear/Record/Note popup fires (and ONLY that popup). A debounced selectionchange still exists as a fallback for non-mouse selection changes (keyboard Shift+Arrow, touch), but while a mouse button is physically down neither function may open.
- Highlight visuals sit BELOW the text ink (`mix-blend-mode:multiply` on `.hlr`): black glyphs stay pure black, the tint only shows through the paper/background underneath.
- Ctrl+click ON a painted highlight = delete it. One action: no confirmation, no popup. That deletion is the ONLY interaction a highlight has.
- A highlight never makes the text clickable and never changes mouseover or the cursor: no click behaviour of its own (a plain click on highlighted text does nothing) and no hover state.
- Ctrl+drag over an existing highlight MERGES HIGHLIGHTS ONLY: any highlight of the same block that overlaps or merely touches the new selection becomes one single highlight, extended to cover both. Overlaps never accumulate as separate highlights. Notes and recordings are never merged, extended, moved or recoloured by a highlight gesture.
- LAYER SEPARATION (owner rule, rework #2): highlights are PAINTED ON THEIR OWN LAYER (`#hlLayer`) — a div of absolutely-positioned translucent rectangles (`.hlr` + `hlr-yellow`/`hlr-red`/`hlr-green`) measured from the text range. A highlight is therefore NOT an element of the text at all; the text DOM belongs to the note/recording layer (mark.nb) alone. Consequence: a highlight may intersect or cross a note/recording in ANY way and both stay whole — nothing is ever refused, split, cloned, moved, hidden or suppressed in either direction, and creating or deleting one never changes the other. `#hlLayer` is `pointer-events:none` (it can never block a click, a drag or a text selection) and carries no z-index (so it creates no stacking context and stays below `.pop`/`#toast`).
- Anchor: the highlighted STRING + (block index, character offset). The offsets are the ruler, so a highlight keeps its place across resize, zoom, font changes and reflow — even while notes/recordings are wrapped around the same characters. Block+offset wins over the text alone, so two identical strings in the same paragraph keep their own places; if that no longer matches (page edited) it falls back to the anchor text, then to nothing.
- The layer may be re-measured (reflow) at any time: window resize/zoom, web-font load, `<details>` open/close and any mouseup repaint the rectangles from the anchors.
- It may span several lines of the same block (paragraph, list item, cell, heading) but never crosses a block boundary (refused with a toast).
- Look: semi-transparent yellow fill that keeps the text readable, rounded ends on every line fragment, no border, no icon.
- After a highlight is created, a tiny colour palette pops above the LAST painted rectangle with three swatches: yellow / transparent red / transparent green. Clicking a swatch recolours the highlight and closes the palette; any click elsewhere closes it too, and so does any other key press. Ctrl and Meta are the exception and never close it: the palette is born while the gesture's own Ctrl is still held down, so that key's keydown (including the auto-repeat the keyboard keeps sending while it stays held) must not close the popup the gesture just opened.
- Coexistence: recording (green underline) and note (very light blue wash) — neither carries a trailing 🎙/📝 icon any more — and the highlight are three separate layers; all three can cover the same span and none of them replaces or triggers another.
- PC only: highlights have no touch gesture.
- Persistence: server row type "hl", anchor = the highlighted string, data = {"color":"yellow|red|green","b":<block index>,"o":<char offset>}; a recolour is a "set" on the same id. Old rows without b/o still restore by anchor text. No backend change needed (add/set/del already accept any type).
- DOM contract: NO highlight element exists in the page text. The only highlight DOM lives inside `#hlLayer`: `div.hlr.hlr-<colour>[data-hlid=<server row id>]`. Notes/recordings stay on mark.nb (has-note / has-rec). The two element sets are never mixed and never nest.

## Note / recording (mark.nb) — owner spec 2026-10-12
- Popup: selecting text (mouse release without Ctrl) opens the six-button popup (see BUTTONS ALWAYS PRESENT below). ONE re-writable note and ONE recording per phrase.
- BUTTONS ALWAYS PRESENT, GREYED WHEN THEY DON'T APPLY (owner spec 2026-10-12): the popup ALWAYS carries the same SIX buttons, in two rows — row 1: ▶ Hear, ▶ Play, ⏺ Record; row 2: 📝 Add/Edit Note, 💾 Save, 🗑 Delete (ids `#pH`/`#pP`/`#pR`/`#pN`/`#pS`/`#pD`). ▶ Hear, ⏺ Record and 📝 Add/Edit Note are ALWAYS clickable. The other three are `disabled` (greyed, never removed) until they apply: ▶ Play only when the phrase has a saved recording; 💾 Save only while a note is being added/edited (the `#nt` textarea is open); 🗑 Delete only when the phrase has a saved note or recording. The popup does NOT repeat the selected text; the saved note, when any, is shown ABOVE the buttons (`#nbNote`) as PLAIN dark text (no blue background, no icon). While recording, the Record button swaps its glyph for the processing SPIRAL; while a saved clip is playing, Play does the same (`nbBtnSpinner`).
- NO TRAILING ICON (owner spec 2026-10-12): the phrase carries NO 🎙/📝 suffix. Recording = green underline only; note = light-blue wash only.
- SAVE APPLIES THE LOOK, NOT THE CLICK (owner spec 2026-10-12): `mark.nb` + its flag are painted by the SAVE only — `markRecording` (called from `rec()` once the clip's bytes are ready) sets `has-rec`; `nbSaveNote` (the popup's 💾 Save) sets `has-note`. Clicking ⏺ Record or 📝 Add/Edit Note paints NOTHING; there is no "immediate mark at the click" any more. `renderLayer` (engine2.js) still must NOT strip or re-derive a flag while a local action is pending (`nbAnyPending`), so a 3s poll never blinks a just-saved mark — and the saved ROW itself stays readable through a poll whose snapshot predates its own write (`nbLocal`/`nbEntries`, see Sync), so the note's text and ▶ Play cannot vanish either.
- ONE BLOCK ONLY (same rule the highlight already uses): a selection that CROSSES a block element (paragraph → list item, cell → cell, heading → paragraph, …) does NOT open this popup. It is refused with a toast (same wording family as the highlight's refusal — "Selecione um trecho dentro de um mesmo bloco.") and the popup stays shut. The check reuses `hlBlockOf`, so the two features can never drift apart.
- IMMEDIATE (owner spec 2026-10-12): the mark is painted the instant the user acts — `recordMark` wraps the selection and sets `has-rec` when Record is clicked, `nbNoting` sets `has-note` when the note is saved — never waiting for a poll. `renderLayer` (engine2.js) must NOT strip or re-derive the flag of an anchor while a local action for it is still inside its grace window (`nbAnyPending`), otherwise a 3s poll blinks the mark off and on: the "appearing and disappearing" this fixes.
- DELETE (owner spec 2026-10-12): 🗑 Delete is always present but enabled only when the phrase already has something saved. One click removes the saved recording, ANY notes of the phrase AND the visual element (mark.nb is unwrapped) — `nbDeleteAnchor` drops the rows from the local `layer` at once, unwraps `mark.nb`, then sends one del per row (network last; NO undo entry is pushed any more — owner spec 2026-10-12). A failed save never undoes what the user just saw.
- DELETE also PURGES THE AUDIO: for a recording the backend's del trashes the Drive file the row points to (b64 column `drive:<fileId>`), so no orphaned audio is left in IAP_uploads; the reply carries `purged:true`, but the frontend shows NO success toast any more (owner spec 2026-10-12: the item visibly leaves the page, and one del goes out per ROW, so the "🗑 apagado ✔" pill fired once per row and read as disconnected from the click). Only a FAILED del still toasts. purgeDrive_ never throws and never blocks the row deletion. The backend `wipe` (teacher reset) purges the same way. Frontend needs no extra field: the row already stores its own fileId.
- Both entry points behave identically: the selection popup (engine1.js `trySelPopup` → `openNbPopup`) and a click on an existing mark (engine2.js `showAnchor`) share the same `nbPopHTML`/`nbWirePopup`/`nbNoting`/`markRecording`/`nbSaveNote`/`refreshNbPopup`/`nbDeleteAnchor` helpers.
- Look: recording = green underline; note = very light blue. Both live on `mark.nb` (the only text-DOM layer); highlights are painted separately on `#hlLayer` and never interact with them. No trailing icon.
- ONE CORE SAVE — `nbUpsert` (owner rule 2026-10-12, "reuse core functions"): 💾 Save (note) and `rec()` (recording) save through the SAME core function. It re-uses the id of the row already stored for that anchor+type, so a re-save/re-record REPLACES that row on the server (never appends a duplicate), updates the local `layer` immediately (the popup and `renderLayer` read the layer — without it the change only appeared at the next 3s poll and an edited note's Save looked like a no-op), then calls `send()`, network last. Consequence for recordings: re-recording over a phrase keeps ONE `rec` row, and the backend trashes the Drive file the replaced row pointed at (`purgeDrive_` inside add/set), so no orphaned clips accumulate in IAP_uploads.
- ADD/EDIT NOTE (owner spec 2026-10-12): 📝 Add/Edit Note opens the `#nt` editor over the SAME popup — every button stays, 💾 Save lights up, and the editor is prefilled with the saved note so a change never silently wipes the old one. Saving paints `has-note`, shows the note above the buttons and leaves the edit state (Save greys again).
- ▶ Play recording fetches the clip on demand — audio is never in the layer, only its Drive `fileId` (uploaded) or inline `b64` (tiny). The bytes come from GET `?action=file&id=…`, become an object URL cached under `a:<anchor>` (the key `rec()` already uses, so a just-recorded clip replays with no fetch), and are played through `new Audio(url)`. The chain is resilient: cached URL first, server fetch with inline-b64 fallback, and one retry-from-server if a stale cached URL errors — the button never dead-ends and never throws into the page. While the clip is playing, ▶ Play shows the processing SPIRAL instead of its glyph (`nbBtnSpinner`): ON at the click (before the Drive/`?action=file` fetch, so a first-ever fetch shows it too) and OFF when playback really stops — `ended` or a failed play/lookup — so it can never get stuck on.

## Undo / Redo — REMOVED (owner spec 2026-10-12)
- There is NO undo/redo button and NO undo stack: the control bar builds no ↶ Undo / ↷ Redo pair (and no "Ctrl+Z=undo" legend), `undoStack`/`redoStack`/`pushUndo`/`applyAction`/`doUndo`/`doRedo`/`setupUndo`/`updateUndoButton` no longer exist in engine2.js, and the page installs no Ctrl+Z/Ctrl+Y handler.
- Deleting a highlight (Ctrl+click), deleting a note/recording (🗑 Delete) and recolouring a highlight are FINAL: the page applies the change at once and the network write follows (network last). Nothing pushes an undo entry any more; re-doing an action takes one click.
- Ctrl+Z inside the note editor is the BROWSER's own text undo (the page no longer intercepts the key).

## Teacher/student control
- There is NO per-student permission level and no visibility toggle anywhere in the code (removed 2026-10-11 as dead code: its value was sent to the server but never read, so it never changed behaviour). Teacher and student see the same page functionality.
- The only teacher-only control is the student selector in the control bar ("demo (you)" + students of the current track); changing it switches which student's layer is loaded and shown.
- No hotkey legend any more: the only hotkey it advertised (Ctrl+Z=undo) went away with the undo feature (owner spec 2026-10-12); sizing per FORMAT.md.

## Sync (cross-session push) — owner spec 2026-10-12
- The ONLY re-check mechanism is a plain poll: `setInterval(loadLayer,3000)` in engine2.js. There is no per-action immediate reload any more (the old `setTimeout(loadLayer,1800)` after every send() is gone) — every add/set/del on either side (teacher or student) reaches the other session within one poll cycle (~3s), not instantly.
- GENERIC GRACE WINDOW: every call to `send(o)` marks `o.id`+`o.action` as "pending" for 6s (`notePending`/`pendingFor` in engine1.js). `renderLayer()` in engine2.js skips re-applying (reverting or resurrecting) any row whose id still has a pending local action — the UI already applied that action directly when the user acted, so a poll snapshot that races ahead of the backend write is simply ignored for that id until the pending window elapses or a later poll confirms the server agrees.
- This mechanism is GENERIC by id+action, not hard-coded per feature (highlight add/color/delete, note add/delete, recording add/delete today) — any future action type routed through `send()` is automatically protected from the same revert-then-reapply flicker with zero additional code. The note/recording layer uses the same window: `nbAnyPending` keeps a freshly created/edited/deleted mark exactly as the click left it until the window elapses.
- THE ROW ITSELF SURVIVES THE POLL, not just the mark (owner report 2026-10-12: a saved note vanished from the phrase and from the popup until the server confirmed the write). `renderLayer` skips a stale ROW, but the poll replaces the whole `layer` with the server snapshot, and every reader of the note/recording layer (the popup's note text `nbNoteText`, ▶ Play's row lookup, `nbHasNote`/`nbHasRec`) reads exactly that row — so a snapshot fetched before the backend write landed made the note disappear for a whole poll cycle. The ONE core save `nbUpsert` therefore also keeps its local copy of the row (`nbLocal`) and `nbEntries`, the single read point of that layer, serves it in place of the snapshot's absent/older copy for as long as the id's own window is open — the same treatment `hlList` gives a freshly painted highlight, using the same `notePending`/`pendingFor` window and no second timer. Notes and recordings both get it, since both save through `nbUpsert`. `pendingFor(id)` returns the MOST RECENT action queued for that id, so a row whose latest local action was a delete (`del`) is never resurrected from `nbLocal`; once the server's row is confirmed the local copy is no longer consulted, and a rejected write drops it when the window expires.
- Lessons are content-only files: config consts (TRACK, LESSON, SECRET, BACKPACK…) + engine includes. Engines/style always ship as full files.
- Gate hash: h(s){let x=0;for(const c of s)x=(x*31+c.charCodeAt(0))|0;return x} applied to email+track+SECRET ("abreportas2025"); invalid/missing gate → redirect to portal.html.
- Backend actions: POST add/set/del/wipe; GET ping/layer/file/dbg. ?action=dbg returns server log. EVERY recording's audio is stored in Drive (IAP_uploads) — the row's b64 column keeps only a `drive:<fileId>` pointer — and del and wipe TRASH that file via purgeDrive_ (never throws), so deleting a recording removes both the row and its audio (reply `purged:true`). (Inline b64 is a last-resort fallback only when the Drive upload itself fails and the clip fits a spreadsheet cell, <45k chars.)
- `?action=layer` returns each recording as `fileId` (Drive) OR `b64` (the inline fallback), so a clip that never reached Drive is still playable after a reload; a page refresh must never turn a saved recording into "no saved audio".
