# FUNCTION — site behaviour contract (engines + backend)
Reference this file whenever a task touches lesson functionality, engines, edit mode or the backend. This file states rules only — no rationale, no history, no dates. The engines implement this file: where an engine disagrees with a rule, the engine is what changes; where a rule blocks a requested change, the rule changes only by owner instruction. A rename or a new internal that the contract names ships with its `FUNCTION.md` line in the same change. Structure/formatting → FORMAT.md · how to design and build a lesson → PEDAGOGY-MAP.md (process) + `<TRACK>-ROADMAP.md` (content) + `<TRACK>-REGISTER.md` (persona, registers) · teaching side → PEDAGOGY.md · state/parameters → STATUS.md.

## What the site does (behaviour architecture)
- "Inglês Abre Portas": a static English-teaching site — one teacher plus allow-listed students, three books (kids, business, adult); every lesson is a standalone page. (Site structure/identity lives in FORMAT.md.)
- A student reads/listens to a lesson and marks it up (highlight, note, record); every mark persists server-side per student and per book, and the teacher sees the same layer via a student selector in the control bar.
- Non-goals: no client-side source of truth (the server is the sole source); the only client-side access list is the teachers in access.json.
- Flow: login (index.html) signs in with Google, checks the server-side access status, and hands a signed `sessionStorage.gate` to `<track>/lessonN.html`. An unrecognized account submits a pending request; the teacher area approves or rejects each request and assigns the student's book at approval.
- **Scope: `.content-area` only.** Every notebook gesture — Hear / Record / Note / Pronunciation Key and Highlight — exists in the lesson content and nowhere else. `engine1.js inContentArea()` gates the two gesture entry points, `trySelPopup()` (the selection popup) and `hlFromSelection()` (the Ctrl highlight), so a selection that starts in the shell — the brand header, the `#barhelp` legend, the control bar, the footer — opens no popup, paints no mark and raises **no toast at all**, the size and one-block refusal messages included (they fire after the gate). The gate is NOT applied to `hlBlocks()`: that block list is the offset ruler every stored highlight is keyed against (`b` in the row), so filtering it would re-index existing rows.

## Persistence & identity
- ALL user data persists server-side (Apps Script Sheet "IAP_backpack!layer" + Drive "IAP_uploads"), and is separate PER STUDENT AND PER BOOK (track). No cross-contamination between students or between tracks.
- Recordings, notes, highlights AND exercise input are all persistent. Exercise answers — filled `input.gap` blanks, picked `fieldset` radios and typed translation textareas — save as `type:"answer"` rows keyed by the field's prompt/stem text with the same {block,offset} tie-breaker as notes/highlights: a reworded prompt or a reordered question stops re-attaching exactly like a reworded phrase, and nothing is deleted on a content change. The `#feed` shared notebook stays `type:"notebook"`. All of it routes through `send()` (outbox + 12s grace window), saves on change + a short debounce + a flush when the tab hides, and an emptied field deletes its row.
- New exercise shapes persist only when authored onto `input.gap`, `input[type=radio]` or a non-feed `textarea`; checkbox / `<select>` / drag-drop answers are not saved by the current engine. Any new activity (a Tier-1 game, a timed drill) must therefore drive one of those three or it leaves no record for the teacher.
- **A radio click is never cancelled.** The browser applies the radio's PRE-CLICK activation (it checks the radio and unchecks its group) *before* it dispatches `click`. The "re-click an option to clear it" behaviour therefore captures the pre-click state on `pointerdown`/`mousedown`/`keydown` and unchecks **after** the click (`ansRadioPre` / `ansRadioTarget` in engine2.js). A click handler must never test `event.target.checked`: it is ALWAYS true there, so testing it cancels every first click and drops the group back to its previous option.
- localStorage must never be a source of truth (the server is the sole source); it holds only the transient outbox of unsent writes for retry — never the data itself.

## Cross-feature principles (override any conflicting wording below)
Shared by Highlight, Note and Recording; the per-feature within/overlap/contain rules in each section below remain in force.
- SHARING: the three may share elements/subfunctions IF AND ONLY IF the behaviour is identical and the sharing causes no conflict or interaction between them. A shared skeleton is fine; any type-specific divergence is isolated by type and never leaks across features. Note and Recording share the one save and the one delete core — the recording-only Drive upload/purge is a type-isolated branch. Highlight does NOT share those save/delete cores: its within/overlap/contain logic is subtract-never-merge. All three share only the behaviour-identical, generic infrastructure — the network write, the id+action grace window, and the block-boundary predicate.
- SEPARATE IDENTITY: the reference strings and files each feature creates are SAVED, CHECKED and DELETED separately. "Checked separately" means each is its OWN row/identity, looked up and resolved as a DISTINCT item — never merged into one row. It does NOT require separate lookup functions: the popup may resolve the note and the recording in one pass (the "same popup" rule requires them together) and still treat them as two independent items.
- VISUAL OVERLAP, NO DATA INTERACTION: they may overlap visually with no conflict and no interaction at the DATA level — a note's row, string or saved content is never altered by a recording, and vice versa. Their marks are SEPARATE visual elements, each carrying only its own identity; when they cover overlapping text they may overlap visually, which is a layout artifact, NOT a data interaction. The ONLY intentional interaction is that a clicked text string or a text selection referencing BOTH a note and a recording shows — and enables interaction with — BOTH through the SAME popup.
- ABUTTING, SAME TYPE: an abutting selection/save of the SAME type has NO interaction with the existing one; the new one is saved separately (its own row). Merely touching (a.end === b.start) is never an overlap.
- HIGHLIGHT within/overlap/contain logic (subtract, never merge) and the colour-change behaviour are MAINTAINED UNCHANGED — see the Highlight section below.

## Highlight (text range)
- Gesture: Ctrl must be held at MOUSEDOWN over the selection; if Ctrl is ALSO held at MOUSEUP, that release creates the highlight. Nothing else creates one (no keyboard-only path, no touch gesture, no automatic path).
- SELECTION IS KEPT: creating a highlight does NOT clear the text selection — the selected text stays selected while the colour palette is open. Choosing a colour (or otherwise dismissing the palette) deselects the text.
- Ctrl at mousedown SUPPRESSES the other selection-based functions for the whole gesture (and ~1.2s after it ends): the Hear / Record / Note popup never opens for a Ctrl gesture, whether or not a highlight ends up being created. A normal selection (no Ctrl at mousedown) still opens that popup exactly as before.
- MOUSE-RELEASE GATE: both functions are decided ONLY at the moment the mouse button is released on a text selection, never mid-drag. If Ctrl is held at that release → the highlight function fires (and ONLY the highlight function). If Ctrl is NOT held at that release → the Hear/Record/Note popup fires (and ONLY that popup). A debounced selectionchange still exists as a fallback for non-mouse selection changes (keyboard Shift+Arrow, touch), but while a mouse button is physically down neither function may open.
- Highlight visuals sit BELOW the text ink (`mix-blend-mode:multiply` on `.hlr`): black glyphs stay pure black, the tint only shows through the paper/background underneath.
- Ctrl+click ON a painted highlight = delete it. One action: no confirmation, no popup. That deletion is the ONLY interaction a highlight has.
- A highlight never makes the text clickable and never changes mouseover or the cursor: no click behaviour of its own (a plain click on highlighted text does nothing) and no hover state.
- Ctrl+drag over an existing highlight SUBTRACTS, NEVER MERGES: the new highlight keeps its WHOLE selection and every character it covers is REMOVED from the highlight(s) already sitting on it, so a second highlight can carry a DIFFERENT colour over text that was already highlighted. What survives of an older highlight keeps its own colour and only shrinks: partly covered → one piece on the SAME row (a `set` with the shorter anchor); the new range strictly inside it → the highlight is SPLIT in two (the first piece keeps the row, the second is a new row, an `add`); fully covered → no character left, its row is `del`eted. Nothing is ever extended to cover an older highlight (no union). A highlight that merely TOUCHES the new range (old.end === new start) shares no character with it and is left untouched, so two same-colour highlights may sit side by side (the seam between them is fine). A whitespace-only piece is never painted, and the trim only runs after the selection passed the usual validation (a whitespace-only selection never deletes anything). Notes and recordings are never merged, extended, moved or recoloured by a highlight gesture.
- LAYER SEPARATION: highlights are PAINTED ON THEIR OWN LAYER — translucent coloured rectangles measured from the text range. A highlight is therefore NOT an element of the text at all; the text belongs to the note/recording marks alone. A highlight may intersect or cross a note/recording in ANY way and both stay whole — nothing is ever refused, split, cloned, moved, hidden or suppressed in either direction, and creating or deleting one never changes the other. The highlight layer never blocks a click, a drag or a text selection, and creates no stacking context (it stays below the popup and the toast).
- Anchor: the highlighted STRING is the reference; the stored (block index, character offset) is only a TIE-BREAKER that picks between two identical occurrences of that string — text identifies the item, position only discriminates between identical candidates, never the other way round. The offsets also keep the highlight's place across resize, zoom, font changes and reflow; if the string no longer matches (page edited) it falls back to the anchor text alone, then to nothing.
- The layer may be re-measured (reflow) at any time: window resize/zoom, web-font load, `<details>` open/close and any mouseup repaint the rectangles from the anchors.
- It may span several lines of the same block (paragraph, list item, cell, heading) but never crosses a block boundary (refused with a toast).
- Look: semi-transparent yellow fill that keeps the text readable, rounded ends on every line fragment, no border, no icon.
- After a highlight is created, a tiny colour palette pops above the LAST painted rectangle with three swatches: yellow / transparent red / transparent green. Clicking a swatch recolours the highlight and closes the palette; any click elsewhere closes it too, and so does any other key press. Ctrl and Meta are the exception and never close it — including the auto-repeat the keyboard keeps sending while that key stays held.
- Coexistence: recording (blue underline) and note (very light blue wash) — neither carries a trailing 🎙/📝 icon — and the highlight are three separate layers; all three can cover the same span and none of them replaces or triggers another.
- PC only: highlights have no touch gesture.
- Persistence: server row type `"hl"`, anchor = the highlighted string, data = `{"color":"yellow|red|green","b":<block index>,"o":<char offset>}`; a recolour is a `"set"` on the same id. Old rows without b/o still restore by anchor text. No backend change needed (add/set/del already accept any type). An overlap is persisted as the SUBTRACTED pieces: the surviving piece stays on the SAME row via a `"set"` (shorter anchor + offsets), a split's second piece is an `"add"` with a fresh id, a fully covered highlight is `"del"`eted — the same three actions, still no backend change.
- DOM contract: NO highlight element exists in the page text — highlights are painted only on their own separate layer (translucent coloured rectangles). Notes and recordings are their own separate elements. The element sets are never mixed and never nest.

## Note / recording
- Popup: selecting text (mouse release without Ctrl) opens the seven-button popup (see BUTTONS ALWAYS PRESENT below). ONE note and ONE recording per phrase — two INDEPENDENT items that are saved, displayed and deleted separately even when both come from the SAME selection.
- POPUP STAYS OPEN ACROSS ITS OWN ACTIONS: none of the popup's own buttons — ⏺ Record (even after the clip saves), 💾 Save, 📝 Delete, 🔊 Delete, ▶ Play, ▶ Hear — closes the popup or clears the text selection; both persist across every action. ONLY a subsequent click, touch or gesture OUTSIDE the popup dismisses it and clears the selection. A keyboard action is NOT a dismissal trigger (the note editor needs the keyboard).
- BUTTONS ALWAYS PRESENT, GREYED WHEN THEY DON'T APPLY: the popup ALWAYS carries the same SEVEN buttons, in two rows — row 1: ▶ Hear, ▶ Play, ⏺ Record, 🔊 Delete; row 2: 📝 Note (becomes 💾 Save while the editor is open), 📖 Pronunciation 🔑, 📝 Delete (ids `#pH`/`#pP`/`#pR`/`#pA`/`#pN`/`#pK`/`#pD`). ▶ Hear, ⏺ Record, 📝 Note/💾 Save and 📖 Pronunciation 🔑 are ALWAYS clickable (Pronunciation is greyed only while its key is already saved). The other three are `disabled` (greyed, never removed) until they apply, and WHAT applies is resolved by ONE call — `nbPopState(t)` (engine1.js): the recording(s) and the note the GESTURE refers to — so no button can disagree with another about which item it acts on. ▶ Play and 🔊 Delete only while EXACTLY ONE recording is involved (that is the clip they play / delete; a selection that merely overlaps one existing recording is enough); 📝 Delete only when the gesture refers to a saved note OR a saved key, and it drops that note and its keys together (the recording, its row, its underline all stay). While MORE THAN ONE recording is involved ▶ Play and 🔊 Delete carry the disabled LOOK (`.locked`, still pressable) and their press only toasts "please select a distinct recording". The popup does NOT repeat the selected text; the saved pronunciation key, when any, is shown BELOW the buttons (`#nbKey`, raw dictionary markup) and the saved note one line below it (`#nbNote`) as PLAIN dark text (no blue background, no icon) — the note is hidden while its editor is open. The blue wash appears whenever a note or a key is saved on the anchor. While recording, the Record button swaps its glyph for the processing SPIRAL; while a saved clip is playing, Play does the same (`nbBtnSpinner`). ⏺ Record is the ONE "always clickable but refuses" button: as soon as ANY recording is involved it carries the disabled LOOK (`.locked`, NOT the `disabled` attribute) and its press only toasts "cannot overwrite recording, delete first" — see the OVERLAP RULES below.
- NO TRAILING ICON: the phrase carries NO 🎙/📝 suffix. Recording = blue underline only; note = light-blue wash only.
- SAVE APPLIES THE LOOK, NOT THE CLICK: the note's wash and the recording's underline are painted by the SAVE only — the recording once the clip's bytes are ready, the note on the popup's 💾 Save. Clicking ⏺ Record or 📝 Add/Edit Note paints NOTHING; there is no "immediate mark at the click". A poll must never strip or re-derive a just-saved mark while its own action is still pending (a 3s poll never blinks it), and the saved ROW itself stays readable through a poll whose snapshot predates its own write, so the note's text and ▶ Play cannot vanish either.
- ONE BLOCK ONLY (same rule the highlight already uses): a selection that CROSSES a block element (paragraph → list item, cell → cell, heading → paragraph, …) does NOT open this popup. It is refused with a toast (same wording family as the highlight's refusal — "Selecione um trecho dentro de um mesmo bloco.") and the popup stays shut. The check reuses `hlBlockOf`, so the two features can never drift apart.

- NOTHING WAITS FOR THE POLL: the mark is painted by the action that saves it — `recordMark` wraps the selection and sets `has-rec` once the clip is saved, `nbNoting` sets `has-note` when the note is saved — never at the next poll. `renderLayer` (engine2.js) must NOT strip or re-derive the flag of an anchor while a local action for it is still inside its grace window (`nbAnyPending`), otherwise a 3s poll blinks the mark off and on.
- DELETE IS SPLIT IN TWO — ONE BUTTON PER ITEM: 📝 Delete (note icon) drops ONLY the note the gesture refers to, 🔊 Delete (audio icon, next to ⏺ Record) ONLY the recording. Both go through the ONE core `nbDeleteItem(t,type)` (engine1.js), which resolves the item with the SAME `nbPopState` its button was rendered from (a selection overlapping a note always addresses that note; a selection overlapping exactly one recording, that recording), drops the rows from the local `layer` at once, drops the clip from the `audioCache` (a deleted recording can never replay from the cache) and removes the mark's OWN flag with `nbUnflag` — which unwraps `mark.nb` only once that flag was the LAST one, so the other item's row, marks and flags survive. Then one `del` per row, network last, and SILENT on success (the item visibly leaves the page). Nothing in this layer is ever changed by a NEW item either: a note created within/overlapping/containing a recording leaves that recording untouched and vice versa, so a note and a recording taken from the same selection are two independent items that live and die independently.
- DELETE also PURGES THE AUDIO: for a recording the backend's del trashes the Drive file the row points to (b64 column `drive:<fileId>`), so no orphaned audio is left in IAP_uploads; the reply carries `purged:true`, but the frontend shows NO success toast (the item visibly leaves the page). Only a FAILED del still toasts. `purgeDrive_` never throws and never blocks the row deletion. The backend `wipe` (teacher reset) purges the same way. The frontend needs no extra field: the row already stores its own fileId.
- Both entry points behave identically: the selection popup (engine1.js `trySelPopup` → `openNbPopup`) and a click on an existing mark (engine2.js `showAnchor`) share the same `nbPopHTML`/`nbWirePopup`/`nbNoting`/`markRecording`/`nbSaveNote`/`refreshNbPopup`/`nbDeleteItem` helpers and the same `nbPopState` resolution of which note/recording the gesture refers to.
- Look: recording = 2px BLUE underline; note = very light blue. Both live on `mark.nb` (the only text-DOM layer); highlights are painted separately on `#hlLayer` and never interact with them. No trailing icon. Both marks are painted INSET — short of the text on each side (a background draw, never padding, so the prose never moves) — so two ABUTTING saves leave a paper gap between them instead of one continuous smear.
- ONE CORE SAVE — `nbUpsert`: 💾 Save (note) and `rec()` (recording) save through the SAME core function. It re-uses the id of the row already stored for that anchor+type, so a re-save REPLACES that row on the server (never appends a duplicate), updates the local `layer` immediately (the popup and `renderLayer` read the layer, so a save is never a no-op until the next poll), then calls `send()`, network last.

- ADD/EDIT NOTE: 📝 Add/Edit Note opens the `#nt` editor over the SAME popup — every button stays, 💾 Save lights up, and the editor is prefilled with the saved note so a change never silently wipes the old one. Saving paints `has-note`, shows the note above the buttons and leaves the edit state (Save greys again).
- ▶ Play recording fetches the clip on demand — audio is never in the layer, only its Drive `fileId` (uploaded) or inline `b64` (tiny). The bytes come from GET `?action=file&id=…`, become an object URL cached under `a:<anchor>` (the key `rec()` already uses, so a just-recorded clip replays with no fetch), and are played through `new Audio(url)`. The chain is resilient: cached URL first, server fetch with inline-b64 fallback, and one retry-from-server if a stale cached URL errors — the button never dead-ends and never throws into the page. While the clip is playing, ▶ Play shows the processing SPIRAL instead of its glyph (`nbBtnSpinner`): ON at the click (before the Drive/`?action=file` fetch, so a first-ever fetch shows it too) and OFF when playback really stops — `ended` or a failed play/lookup — so it can never get stuck on.

- OVERLAP RULES. A row is keyed by its anchor = the text it covers, so two actions interact exactly when their SPANS share a character; merely TOUCHING (a.end === b.start) is not an overlap and both stay whole.
  - ABUTTING is legal and ordinary. The stored anchor is the TRIMMED selection, so a mark covers exactly its own anchor text and two abutting saves never share the boundary space. `findRange` also walks text INSIDE `mark.nb` (an anchor that abuts or crosses a mark stays findable).
  - A selection that is INSIDE, OVERLAPS or CONTAINS an existing RECORDING (an audio file) LOCKS ⏺ Record, and that includes covering the recording EXACTLY. A click on the phrase's own mark is locked the same way: with no selection, the mark's own anchor span is what the gesture refers to. The button is rendered with the disabled LOOK (`.locked`, NOT the `disabled` attribute) and pressing it raises the toast "cannot overwrite recording, delete first" instead of recording; the clip has to be deleted (🔊 Delete) first. A selection that merely ABUTS a recording (shares no character with it) is an ordinary new phrase and records normally.

  - The SAME resolution drives ▶ Play and 🔊 Delete: a selection inside, overlapping, or containing ONE recording enables ▶ Play for THAT clip — and 🔊 Delete for it; a selection touching or containing MORE THAN ONE recording disables both, which then carry the disabled LOOK and toast "please select a distinct recording". Neither button ever touches the other item: deleting the recording keeps the phrase's note (its row and its blue wash) and deleting the note keeps the recording (its row and its underline).
  - A selection that overlaps or CONTAINS a NOTE makes that note the ACTIVE note: the popup is about the note's OWN anchor (its row, its saved text shown above the buttons, its editor prefilled). 💾 Save then EXPANDS the note's AREA to the new selection — the union of the two spans — and the union's own text becomes the note's new anchor; the row keeps its id (a `set`, never a duplicate row). A selection strictly INSIDE the note references the note the same way but RETAINS THE ORIGINAL STRING as its reference (no re-anchoring): only the note's text changes. The expansion wraps the UNION first (`nbWrap` MOVES the covered nodes into the new mark, it never clones) and only then removes the note flag from the note's own, now-stale pieces (`nbUnflag`) — a piece that also carries a recording stays — so growing a note can never delete, move or re-paint the recording inside it.
  - A mark may be painted by MORE THAN ONE element: a note/recording painted ACROSS an older mark's edge SPLITS it into pieces that all keep its `data-a` and its flags, so its span is still measurable as a whole, BOTH actions stay displayed at the same time, and the older row is never deleted, moved or recoloured. Wrapping goes through `nbWrap` (engine1.js), which moves the covered nodes into the new mark without cloning. Overlap is resolved when the popup opens (`openNbPopup` → `nbSelArea`/`nbPickNote`/`nbExpandPlan`/`nbPopState`), all measured with the highlight's own ruler (`hlBlocks`/`hlOffset`), so the two features can never disagree about where a span is.

## Teacher/student control
- The only teacher-only control is the student selector in the control bar ("demo (you)" + students of the current track); changing it switches which student's layer is loaded and shown.
- **Student landing page (index.html)**: the student index is **three track columns** (kids · business · adult), one per book. Each column lists that book's lessons from `lessons.json`; **each row reads `NN. Lesson Name`** (zero-padded number, then the title) on **one line** — a long title truncates with an ellipsis instead of wrapping past the column, and the full name stays available as a `title` tooltip; progress is a colour (a finished lesson turns teal) rather than an emoji. **The whole entry is the link** to the page (there is no per-lesson button), and **"▶ Continuar da lição N" sits at the TOP of the list**. A book the student does not hold is **greyed out and inert** with "sem acesso", and `go()` refuses it — a locked column is advertising, never a way in. `status.tracks` decides which columns are live (multi-track access, above). The page opens with a one-line colourful intro (English line + its Portuguese line below); signing out stays in the control bar.
- **Granting a second book**: the teacher area's approved list shows one jump button and one `× Book` removal per held book, plus a `＋ dar acesso` control offering the books the student does not have yet.

## Edit mode (teacher-only)
- ✏️ Edit (teacher-only, in the "demo (you)" view): a ✏️ Edit toggle loads a separate unmarked, editable copy — the live page and its marks are never touched. Changes save to the backend when you click ✔️ Done, as a `type:"content"` row holding the FULL page HTML, keyed to the teacher's email (staging only; students never see it), and ↩️ Revert discards them.
- Every lesson file is created with a sibling `<lesson>.edit.html` sidecar that is a full copy of the lesson.
- Committing an edit is a FULL OVERWRITE by default (when the owner says "I edited lesson X"): fetch the `type:"content"` row, write its full-page `data` over the lesson file — INCLUDING the content header (the `<h1>` title) and the opening block(s) directly below it (the `abertura` / how-to-read cards), never only the numbered sections — and re-copy the sidecar; a narrower scope happens only if the owner asks. The edit content is a server-side `type:"content"` sheet row, NOT a local file — retrieve it via GET `<BACKPACK>?action=layer&email=<teacher email>&lesson=<n>` → JSON `{rows:[…]}`; take the `type:"content"` row's `data` (the BACKPACK exec URL is in STATUS.md). The agent fetches that URL directly with a GET — no credentials needed, so bake-in requires no copy-pasting.

## Engines & pages
- engine1.js = gate (sessionStorage sig check), selection popup (the seven always-present buttons ▶ Hear / ▶ Play / ⏺ Record / 🔊 Delete / 📝 Note·Save / 📖 Pronunciation 🔑 / 📝 Delete, greyed when they don't apply, see Note/recording above — opened at mouse release, never mid-drag, and never for a selection that crosses a block element), Ctrl text-range highlight gestures painted on their own layer (#hlLayer: create on Ctrl+mouseup / subtract an overlap / delete / colour palette, popup suppressed for the whole Ctrl gesture), recording (stops after 2s silence, 🎙 indicator, 10s countdown), recording playback (nbPlayRecording via ?action=file), notes, anchors, send() to backend, persistent write outbox + generic local-action pending registry (outbox/notePending/pendingFor, see Sync below), and the shared note/recording helpers (nbUpsert/nbEntries/nbAnyPending/nbHasRec/nbHasNote/nbNoteText/nbNoteDisplay/nbKeyText/nbKeyLookup/nbDeleteKeyRows/nbDeleteNoteKey/nbNoteEditorClose/nbPopHTML/nbWirePopup/openNbPopup/markRecording/nbNoting/nbSaveNote/refreshNbPopup/nbPlayRecording/nbUnmark/nbDeleteAnchor).
- engine2.js = control bar, layer poll (adaptive, see Sync below), highlight render/delete (#hlLayer rectangles rebuilt from the server rows: hlRestore/hlDrop/hlReflow), note/recording render (mark.nb flags, gated by nbAnyPending), showAnchor (reuses engine1's popup helpers).
- pronkey.js = pronunciation-key engine (window.PronKey): parses a word / text string into whole words (partial words thrown out) and looks each word up in the custom dictionary (root dictionary.json → PronKey — the single source of truth for the key's rules + data). The popup's 📖 Pronunciation 🔑 button calls PronKey.lookup (one key per word) and persists the word's key as a `key` row shown below the buttons (the blue wash marks it). The dictionary stores compact notation (no HTML: `-` syllable demarcation, `[x]` hanging/grey letters, `ə` schwa); PronKey.render() expands it to HTML for display.
- engine3.js = **Tier-1 generic games** (`window.GAMES`, first game `shootPair`). The page keeps the real answers: a `.game[data-game="shootPair"]` block holds `.game-start`, an authored `.game-how`, and a `.game-list` of ordinary `.qitem`s (stem + optional `.listen` + `input[type=radio]` options). The engine only **animates and marks** those radios — a hit checks the option and dispatches `input`/`change`, so the answer persists through the normal `type:"answer"` path; a miss leaves the radio untouched (a blank is the teacher's evidence). Levers on the element: `data-skin` (`duck` | `ufo` — shape + flight style, so a new target is data, not code), `data-speed` (px/s, default 110), `data-limit` (countdown seconds, 0 = off), `data-replay` (missed items return once, default on). Sequence per item: prompt fades in 1s → 2s to takeoff → targets cross the stage → shoot; a wrong shot, an expired countdown or targets leaving the screen are all a miss (0 points, hit = 1). Start is the only entry point (no autoplay). Degrades to the plain radio list without JS, prints as that list, and is keyboard- (1…n / Enter) and touch-operable.
- **Audio for `.listen` buttons (▶).** Every `data-say="…"` string is pre-rendered to a clip by `build-audio.mjs` (local Kokoro-82M neural TTS, voice `af_heart` = neutral US female) into `audio/<sha1>.mp3`, indexed by `audio/manifest.json` (`clips: { "<exact data-say text>": "<file>" }`). `playSay(text[,rate])` (engine2, exposed as `window.playSay`) plays the clip, honours an optional `data-rate` on the button via `playbackRate`, stops whatever was playing, and **falls back to `speechSynthesis`** when the page is opened from `file://`, the manifest is unreachable, or the string has no clip (e.g. text selected in the popup) — the fallback picks a natural en-US female voice instead of the OS default. engine1's popup ▶ Hear uses the same helper. `npm run build:audio` renders + merges the manifest (never truncates it); `npm run audio:check` lists `data-say` strings still lacking a clip (publish gate). Rule for content: **`data-say` carries how the line is *said*, not how it is written** (`R$ 1.250` → `data-say="one thousand two hundred fifty reais"`).

## Backend (source of truth: backend/Code.gs)
### What it is
- ONE Google Apps Script web app (`backend/Code.gs`), deployed on the owner's account (I cannot deploy). Every lesson page points at the same deployment through `const BACKPACK` (exec URL in STATUS.md).
- It is the only server: the frontend is static GitHub Pages, so all shared state lives here.
- Storage: sheet `IAP_backpack!layer`, columns `id | email | track | lesson | type | anchor | data | author | ts | b64`, plus sheet `IAP_backpack!access` (columns `email | name | track | status | ts`) for the approved-student list and the pending-request queue, plus the Drive folder `IAP_uploads` for recording audio.
- Separation is enforced on READ *and* on WRITE by `email + track + lesson` — no cross-student and no cross-book visibility, teacher tools included.
### API
- GET `?action=ping` → health check · `?action=layer&email=…&lesson=…` → every row for that student+lesson (what engine2.js polls — adaptively) · `?action=file&id=<fileId>` → the recording bytes from Drive · `?action=dbg` → server info · `?action=students&track=…` → the approved-student list for that book (used by the teacher's student selector in the control bar).
- POST (JSON body): `add` (new row, id minted if absent) · `set` (replaces the row that has the same id — this is what the ONE core save uses for note re-save / clip re-record) · `del` (removes every row with that id) · `wipe` (teacher reset for one email+lesson, or everything when no email is given).
- POST access-control (JSON body, Google ID token required and verified server-side): `status` (report an email's status — approved / pending / unknown; approved carries **`tracks:[…]`**, every book the student holds, plus `track` = the first for old callers) · `request` (record a pending signup request) · `approve` (teacher-only; grants **ONE** book — calling it again for the same student adds **another** book, so a student can hold several tracks at once; a track-less pending request is upgraded rather than duplicated) · `reject` (teacher-only; removes the pending request) · `remove` (teacher-only; removes ONE book when a `track` is given, the whole student otherwise — access only, their lesson rows stay) · `queue` (teacher-only; returns the pending requests and the approved students **grouped per student** as `{email,name,tracks:[{track,lastCompleted}]}`). approve/reject/remove/queue also verify the caller is a teacher.
- **The access sheet is one row per EMAIL+TRACK.** A student's second book is a second row (`IAP_backpack!access`: email | name | track | status | ts); nothing overwrites the first. The landing page reads `status.tracks` and renders all of them.
- Writes are network-last: the popup/layer updates immediately, the POST follows. Only the layer rows are read back, so a backend edit never needs a frontend change.
### Rules that must not drift
- A recording's audio always goes to Drive; the row keeps a `drive:<fileId>` pointer in the `b64` column. Inline base64 is a last-resort fallback only when the upload itself fails (clip must fit a spreadsheet cell, <45k chars).
- `del`, `set` (replacing a row) and `wipe` also TRASH the Drive file they orphan (`purgeDrive_` never throws and never blocks the row delete) — no orphaned audio left in IAP_uploads.
- Every recording row carries its own fileId, so the frontend can play (`?action=file&id=`) or delete a clip without any extra field.
- A script lock serializes POSTs; every response is JSON (`{result}` / `{count,purged}` / `{error}`) and every thrown error comes back as `{error}`.
- Access-control actions verify the Google ID token server-side (tokeninfo, audience = CLIENT_ID) before trusting an email; approve/reject/queue additionally verify the caller is a teacher (the TEACHERS constant, kept in sync with access.json). The `access` tab holds students+requests and must never be read or written as `layer` rows.
- A Code.gs edit only takes effect after a NEW deployment version (Deploy → Manage deployments); the `/exec` URL does not change, so pages need no update.
- The jsdom harnesses mock `fetch` and never call this backend for real: verify a backend change by the diff plus the affected code path (a real curl against the deployed URL only when the risk is real).

## Sync (cross-session push)
- The ONLY re-check mechanism is an adaptive poll in engine2.js — 1s while the tab is visible and there is recent activity (a user input OR a poll that just saw a change), 5s only after 1 minute of neither, and paused while the tab is hidden — every add/set/del on either side (teacher or student) reaches the other session within one poll cycle (~1s while active), not instantly.
- WRITES GO THROUGH A PERSISTENT OUTBOX: `send()` queues the op in a localStorage outbox (keyed per user+track+lesson) and flushes it ONE fetch at a time (300ms coalesce, serial, retried with backoff on failure), so rapid actions can never burst the backend with concurrent POSTs and a failed write survives a reload and is retried until the server confirms it. The server stays the sole source of truth; the outbox only remembers unconfirmed deltas, and each op keeps a stable id (the backend add/set/del are idempotent by id) so a retry lands exactly once.
- GENERIC GRACE WINDOW: every call to `send(o)` marks `o.id`+`o.action` as "pending" for 12s (`notePending`/`pendingFor` in engine1.js). `renderLayer()` in engine2.js skips re-applying (reverting or resurrecting) any row whose id still has a pending local action — the UI already applied that action directly when the user acted, so a poll snapshot that races ahead of the backend write is simply ignored for that id until the pending window elapses or a later poll confirms the server agrees.
- This mechanism is GENERIC by id+action, not hard-coded per feature (highlight add/color/delete, note add/delete, recording add/delete today) — any future action type routed through `send()` is automatically protected from the same revert-then-reappear flicker with zero additional code. The note/recording layer uses the same window: `nbAnyPending` keeps a freshly created/edited/deleted mark exactly as the click left it until the window elapses.
- THE ROW ITSELF SURVIVES THE POLL, not just the mark. `renderLayer` skips a stale ROW, but the poll replaces the whole `layer` with the server snapshot, and every reader of the note/recording layer (the popup's note text `nbNoteText`, ▶ Play's row lookup, `nbHasNote`/`nbHasRec`) reads exactly that row — so a snapshot fetched before the backend write landed would make the note disappear for a whole poll cycle. The ONE core save `nbUpsert` therefore also keeps its local copy of the row (`nbLocal`) and `nbEntries`, the single read point of that layer, serves it in place of the snapshot's absent/older copy for as long as the id's own window is open — the same treatment `hlList` gives a freshly painted highlight, using the same `notePending`/`pendingFor` window and no second timer. Notes and recordings both get it, since both save through `nbUpsert`. `pendingFor(id)` returns the MOST RECENT action queued for that id, so a row whose latest local action was a delete (`del`) is never resurrected from `nbLocal`; once the server's row is confirmed the local copy is no longer consulted, and a rejected write drops it when the window expires.
- Lessons are content-only files: config consts (TRACK, LESSON, SECRET, BACKPACK…) + engine includes; engines and style.css stay single shared files, never inlined per lesson.
- Gate hash: h(s){let x=0;for(const c of s)x=(x*31+c.charCodeAt(0))|0;return x} applied to email+track+SECRET ("abreportas2025"); invalid/missing gate → redirect to index.html.
- `?action=layer` returns each recording as `fileId` (Drive) OR `b64` (the inline fallback), so a clip that never reached Drive is still playable after a reload; a page refresh must never turn a saved recording into "no saved audio".
