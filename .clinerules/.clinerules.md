# TOOL DISCIPLINE
- **Reading large files (truncation).** A read that comes back TRUNCATED — an elided span `[truncated N chars]`, or a line total longer than the text returned — is paged with `start_line`/`end_line` (chunks well under ~6000 characters; a character-dense file may need 15–20 lines) until the whole file is read; rely on the union.
- **Command output.** Bound it to ~40 lines: `Select-Object -First 40`, `Measure-Object` for a count, or a relevance filter (`Select-String 'error|fail|✖'`) when the cause is not at the end. Unknown-length commands (`npm run`, `node`, suites, `git`) take a filter then `-Last 40` (the failure is usually last). Where the ceiling would cut items that matter, give the count plus the first failing item as `path:line`. The goal is minimising error and not crashing VS Code, not token thrift.
- **Split a large write before sending it.** Above ~6000 characters a single edit is refused: split at a section boundary first, never send, fail, then split.
- **QA needs a stated reason.** For any QA or Verification step, state which problem it solves; 'confirming' is not sufficient without a defensible, stated basis for doubt. Non-existence of a stated, extant problem means the QA is an error.
- **A check is as wide as its doubt.** The stated reason names the file and the edit that put it at risk, and the command's reach is the pair: an audit of one page opens one page. Where the reach cannot be narrowed — the sweep *is* the question — the reply says so before the run. An unfamiliar flag is read at its definition before it is trusted to mean "just this one"; a harness given an argument shape it does not recognise answers with its own default scope. Findings from files the ask never named are the reach, not evidence about the ask, and the reply names each one's page.
- **Never restate tool output.** Report the outcome — "3/3 pass", "exit 0", "542 deletions" — with the path. No quoted blocks, no diff recaps; a table only to compare three or more things.
- **Before patching a file you have not read this turn, read the region you are anchoring to.** An anchor rebuilt from memory is a guess: it either fails or matches the wrong place


## TOOL / TERMINAL PARAMETERS
The shell reports the true exit code (`$LASTEXITCODE`); Cline's capture of it does not — it often misreports a succeeded command as code 1, so work WITH that:
- Judge a call by its printed output, never the reported exit code.
- Commands in one call run concurrently: anything that must happen in order goes in one `;`-chained string.
- When the exit code matters, print it in the command: `& node qa/content.mjs; 'EXIT=' + $LASTEXITCODE`.
- A captured chunk may open with a leaked terminal-title escape, and capture failure falls back to raw scrollback: keep commands short (reliability, not tokens) and re-run rather than trust a torn buffer.
- Non-ASCII can arrive as mojibake — confirm with an ASCII marker (`Write-Output 'MARKER_OK'`) and read files via `read_files`/`search_codebase`, not shell echo.
- NEVER run a bare `exit` / `exit <n>` (it closes the terminal); print the value or `throw` instead.
- A session may be logged `status: failed` / `exit_code 1` after a real success — that log status is noise.

# ADHERENCE 
- For any user [phrase, instruction, or intent] [that has multiple plausible interpretations], stop and ask a question to hone your interpretation.
- Use the shortest wording that keeps 100% of the information (**concise**). Never invent or imply terminology.  Never soften, modify, or reinterpret a request.
- If prompt instructs or requires a condition, makes a specific request, or sequences steps, these elements must be strictly followed. 
- For each element of the prompt, categorize:
	a) An instruction to act - **no other plausible interpretation**].
	b) Questions, examples, statements, issue reports  (eg. "can you X", "I think X should Y") - may modify (a) items but are never standalone instructions.
- Make a judgement call - "How and in what order will the [the elements/goals of the prompt] be batched? Consider:
		- Questions and planning steps should be dealt with first.
		- User instructions - eg. "Do X, then Y" -).
		- Interconnectivity and/or prerequisites. (any item which depends on or benefits from the completion of another is put in a seperate and subsequent batch).
		- Context Clarity  (Steps benefit from being batched together when the files they will need to read or the context they will create is similar).
		- Efficiency (time efficiency supercedes token efficiency).
