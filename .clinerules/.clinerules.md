## **Before responding to any prompt, read `ADHERENCE.md` at the repo root and parse the prompt by it.**

# TOOL DISCIPLINE - 
- **Reading large files (truncation).** For any file read that comes back TRUNCATED — an elided span marked `[truncated N chars]`, or a reported line total longer than the text returned — page through it in bounded chunks with `start_line`/`end_line` (each chunk well under ~6000 characters; a character-dense file may need as few as 15–20 lines) until the whole file has been read, then rely on the union of the chunks.
- **Command output.** Bound it to ~40 lines — `Select-Object -First 40`, `Measure-Object` for a count, or a relevance filter (`Select-String 'error|fail|✖'`) when the cause is not at the end. Unknown-length commands (`npm run`, `node`, suites, `git`) take a filter then `-Last 40`, since the failure is usually last. When the ceiling would cut items that individually matter, give the count plus the first failing item as `path:line`. The goal is not token thrift: it is minimising error, and keeping command output small enough that it does not crash VS Code.
- **Split a large write before sending it.** The editor refuses a single edit above roughly 6000 characters, so a payload approaching that ceiling is split at a section or block boundary BEFORE the first call — never sent whole, seen to fail, and split afterwards: the refusal costs exactly the work the pre-split would have, and leaves a half-applied file in the between-time. The `$env:TEMP` build plus one `Move-Item` swap under "Never rebuild a file by truncating it" is the same discipline at whole-file scale.
- **QA needs a stated reason.** For any QA or Verification step, state which problem it is solving ('confirming' is not sufficient need without a defensible, stated basis for doubt) non-existence of a stated, extant problem means the QA is an error.
- **A check is as wide as its doubt.** The stated reason names the file and the edit that put that file at risk, and the command's reach is the pair: an audit of one page opens one page. Where the reach cannot be narrowed — the sweep *is* the question — the reply says so before the run. A harness asked in an argument shape it does not recognise answers with its own default scope: `qa/overflow.mjs` read a page path as "no lesson named" and audited all three tracks, so an unfamiliar flag is read at its definition before it is trusted to mean "just this one". Findings that arrive from files the ask never named are not evidence about the ask — they are the reach, showing itself — and the reply names the page each one came from.
- **Never restate tool output.** Report the outcome — "3/3 pass", "exit 0", "542 deletions" — with the path. No quoted blocks, no diff recaps; a table only to compare three or more things.
- **Decide what a result's size means before running the command.** If the question is exploratory — an unbounded search, a look around — a large result means the question was wrong; narrow it and re-run. If the command IS the answer — a count, an audit, an anchor read, a rule file, an expensive or one-shot run — consume it at whatever size, and never narrow when completeness is the requirement. Do not narrate the waste either way.
- **Never rebuild a file by truncating it.** `$l[0..N] | Set-Content`, `-TotalCount N | Set-Content` and their kin leave the file broken if the next call does not complete — and a file cut to its first N lines still opens and still looks valid. Patch by anchor. When a whole body must be rebuilt, build it in `$env:TEMP`, check it whole, then swap it in with one `Move-Item`.
- **Before patching a file you have not read this turn, read the region you are anchoring to.** An anchor rebuilt from memory is a guess, and a guessed anchor either fails or matches the wrong place.
- **Ask vs search:** a product or pedagogy decision the user can answer in one sentence is asked, not explored. A code lookup — where a class lives, whether a primitive exists — is searched, never asked.
- **Drift has an address.** When the steps leave what the prompt named — another file, another folder, the tooling beneath it — that step carries one clause saying what it is for and how it returns to the ask, and the second step still off the prompt is where the prompt gets re-read before the next call. The test is checkable in the transcript: which line of the task did this step serve?

## TOOL / TERMINAL PARAMETERS
The shell reports the true exit code (`$LASTEXITCODE`); Cline's capture of it does not — it often misreports a succeeded command as code 1, so work WITH that:
- Judge a call by its printed output, never the reported exit code.
- When the exit code matters, print it in the command: `& node qa/content.mjs; 'EXIT=' + $LASTEXITCODE`.
- A captured chunk may open with a leaked terminal-title escape, and when capture fails it falls back to raw scrollback — keep commands short (reliability, not tokens) and re-run rather than trust a torn buffer.
- Non-ASCII can arrive as mojibake — confirm with an ASCII marker (`Write-Output 'MARKER_OK'`) and read files via `read_files`/`search_codebase`, not shell echo.
- NEVER run a bare `exit` / `exit <n>` (it closes the terminal); print the value or `throw` instead.
- A session may be logged `status: failed` / `exit_code 1` after a real success — that log status is noise.
